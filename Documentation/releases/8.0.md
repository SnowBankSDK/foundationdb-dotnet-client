# FoundationDB .NET client 8.0

Released on YYYY-MM-DD.

In this release: FdbLite, an on-disk storage engine that speaks the FoundationDB transaction API
without a cluster, becomes the emulator's storage engine and a local store for standalone processes.

## Highlights

- **FdbLite** is a single-node, on-disk key/value engine (a copy-on-write B+tree over a memory-mapped
  file) that runs the same read-your-writes transaction machinery as the in-memory FakeDb: snapshot
  reads, read-conflict tracking, atomic mutations, versionstamps, watches and selector resolution,
  with the same semantics the real cluster has. It fills the role SQLite fills for SQL: an
  application, an edge node or a test opens a file (or an in-memory store) and runs unchanged layer
  code against it. The in-memory FakeDb is now one storage backend of that shared machinery, and the
  emulator, the engine and the client share one transaction implementation in `FoundationDB.Client`.
- `FakeDbStore` and the in-memory backend classes moved from the `FoundationDB.Testing` namespace to
  `FoundationDB.FakeDb`, and the snapshot retention types to `FoundationDB.Storage`. A `using` line
  fixes every affected project.

# FoundationDB

## FdbLite: the FoundationDB transaction API in one process, on disk

If an edge node, a command-line tool or a test needs the FoundationDB transaction API without a
cluster, and the in-memory FakeDb loses everything when the process exits, `FoundationDB.FdbLite` is
the store to open.

FdbLite is a single-process key/value store: a copy-on-write B+tree over a memory-mapped file, with
crash-safe commits, behind the same read-your-writes transaction machinery as FakeDb (snapshot reads,
read-conflict tracking, atomic mutations, versionstamps, watches, key selectors). Layer code written
against `IFdbDatabase` runs on it unchanged. One process opens a given file at a time; there is no
network, no replication and no tenant isolation.

| | `FoundationDB.FakeDb` | `FoundationDB.FdbLite` |
|---|---|---|
| Data lives | in memory, gone at process exit | in a file (or in memory on request) |
| Versions kept by default | the last 5 seconds | a recent-version window; older pages are reclaimed |
| Registration | `services.AddFakeDb(730)` | `services.AddFdbLite(730, path)` |
| Direct open | `new FakeDbStore(730)` | `FdbLiteStore.OpenOrCreateFile(path, FdbLiteGeometry.Default, apiVersion: 730)` |
| Targets | `net8.0`, `net10.0`, `net11.0`, `netstandard2.0` | `net10.0`, `net11.0` |

Install the package:

```
dotnet add package FoundationDB.FdbLite
```

```xml
<ItemGroup>
  <PackageReference Include="FoundationDB.FdbLite" Version="8.0.0" />
</ItemGroup>
```

Register it where a cloud node calls `AddFoundationDb(...)`. `AddFdbLite` provides the same
`IFdbDatabaseProvider`, so the code that opens transactions is the regular client API:

```csharp
using FoundationDB.FdbLite;

// a file-backed store, created on first start (the parent folder too)
builder.Services.AddFdbLite(730, "/var/lib/acme/agent/state.fdblite");
```

`AddFdbLite(730)` without a path opens an in-memory store that dies with the provider. The
`configure` callback sets `Geometry` (page size of a new file, 32 KiB by default), `Retention`
(`FdbSnapshotRetention.KeepEverything` for a forensic run), `Time`, a read-only mode or transaction
logging. `AddFdbLite(store)` shares one `FdbLiteStore` between several providers; the caller
disposes it.

### Example: a process keeps its own state across restarts

A process with no cluster (an edge node, a command-line tool) can count its starts and keep the last
configuration it received, so a restart applies that configuration before any remote link is up.

1. Reference the package (above), and register the store, one file per process:

```csharp
using FoundationDB.FdbLite;

var localStorePath = builder.Configuration["LocalStore:Path"]
	?? Path.Combine(Environment.GetFolderPath(Environment.SpecialFolder.LocalApplicationData), "Acme", "Agent", "state.fdblite");
builder.Services.AddFdbLite(730, localStorePath);
builder.Services.AddSingleton<AgentLocalState>();
```

2. Write the state class over the provider. Keys are built with `subspace.Key(...)` under a directory
resolved per transaction, values with `FdbValue.*`, the counter with an atomic add. A fresh store has
no directories, so the write paths use `ResolveOrCreate` and the read path `TryResolve`:

```csharp
public sealed class AgentLocalState
{
	private const int SUBSPACE_BOOTS = 0;  // (0,) -> fixed64 little-endian: number of starts
	private const int SUBSPACE_CONFIG = 1; // (1,) -> json: the last configuration received

	public AgentLocalState(IFdbDatabaseProvider db)
	{
		this.Db = db;
		this.Location = db.Root["Agent"];
	}

	private IFdbDatabaseProvider Db { get; }

	private FdbDirectorySubspaceLocation Location { get; }

	public async Task<long> RecordBootAsync(CancellationToken ct)
	{
		var db = await this.Db.GetDatabase(ct);
		return await db.ReadWriteAsync(async tr =>
		{
			var subspace = await this.Location.ResolveOrCreate(tr);
			var key = subspace.Key(SUBSPACE_BOOTS);
			long boots = (await tr.GetAsync(key)).ToInt64() + 1;
			tr.AtomicAdd64(key, 1);
			return boots;
		}, ct);
	}

	public async Task<JsonValue?> LoadConfigAsync(CancellationToken ct)
	{
		var db = await this.Db.GetDatabase(ct);
		return await db.ReadAsync(async tr =>
		{
			var subspace = await this.Location.TryResolve(tr);
			if (subspace == null) return null;
			var value = await tr.GetAsync(subspace.Key(SUBSPACE_CONFIG));
			return value.IsNullOrEmpty ? null : JsonValue.ReadOnly.Parse(value.Span);
		}, ct);
	}

	public async Task SaveConfigAsync(JsonValue config, CancellationToken ct)
	{
		var db = await this.Db.GetDatabase(ct);
		await db.WriteAsync(async tr =>
		{
			var subspace = await this.Location.ResolveOrCreate(tr);
			tr.Set(subspace.Key(SUBSPACE_CONFIG), FdbValue.ToJson(config));
		}, ct);
	}
}
```

3. Use it at startup: record the start, then apply the cached configuration:

```csharp
long bootCount = await localState.RecordBootAsync(stoppingToken);
var cachedConfig = await localState.LoadConfigAsync(stoppingToken);
if (cachedConfig != null) ApplyConfig(cachedConfig);
```

Call `SaveConfigAsync(config, ct)` each time a new configuration arrives.

## `AddFakeDb` opens the cluster root when no root is given, and reports availability

`services.AddFakeDb(730)`, the one-liner the package README documents, failed at the first
transaction with `ArgumentException: Directory Subspace path must absolute`, because an omitted
`root` argument is the relative empty path and not the cluster root. It now opens the cluster root
(`FdbPath.Root`); `AddFakeDb(730, FdbPath.Root)` behaves as before. `FakeDbProvider.IsAvailable`
was `false` for the provider's whole life; it is `true` once the database is open. `AddFdbLite` has
the same two behaviors.

## `FakeDbStore` moved to the `FoundationDB.FakeDb` namespace

If a project that names `FakeDbStore` (or `ColaBackend`, `ColaCommittedStore`) stops compiling with
"the type or namespace name could not be found", this section is the fix.

`FakeDbStore` and the in-memory backend classes moved from the `FoundationDB.Testing` namespace to
`FoundationDB.FakeDb`. In 7.4.x the store class is declared in `FoundationDB.FakeDb/FakeDbDatabase.cs`
under `FoundationDB.Testing`; in 8.0 the emulator is restructured over the storage engine and the
store class lives in `FoundationDB.FakeDb/FakeDbStore.cs` under `FoundationDB.FakeDb`.
`FakeDbProvider`, its options, and the `AddFakeDb` registration stay in `FoundationDB.Testing`.

| | 7.4.x | 8.0 |
|---|---|---|
| Namespace of `FakeDbStore` | `FoundationDB.Testing` | `FoundationDB.FakeDb` |
| Namespace of `FakeDbProvider`, `AddFakeDb` | `FoundationDB.Testing` | `FoundationDB.Testing` (unchanged) |
| Namespace of `FdbSnapshotRetention`, `FdbSnapshotRetentionPolicy`, `FdbSnapshotRetentionContext` | `FoundationDB.Testing` (assembly `FoundationDB.FakeDb`) | `FoundationDB.Storage` (assembly `FoundationDB.Client`, shared with FdbLite) |

Affected: every project that names `FakeDbStore`, a backend class or a retention type with only
`using FoundationDB.Testing;` in scope.

What to do: add `using FoundationDB.FakeDb;`, and `using FoundationDB.Storage;` where a retention
policy is selected. A `global using` in the project's `GlobalUsings.cs` covers the whole project:

```csharp
global using FoundationDB.FakeDb;
global using FoundationDB.Storage;
```
