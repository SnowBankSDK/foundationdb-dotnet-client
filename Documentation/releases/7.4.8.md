# FoundationDB .NET client 7.4.8

Released on YYYY-MM-DD.

## Client metrics count each completed operation once

If a dashboard or an alert reads `db.fdb.client.operations.completed` or the failed attempts of
`db.fdb.client.operations.size`, this section concerns you.

- `db.fdb.client.operations.completed` counted a write transaction that committed twice: once at the
  commit, and once at the end of the attempt. A read-only transaction was counted once. 7.4.8 counts
  every completed attempt once, so the counter of a write workload drops by half. The tags are
  unchanged: `operation.retries` and `operation.status`.
- `db.fdb.client.operations.size` tagged the size of a failed attempt with `operation.status=Success`.
  7.4.8 tags it with the error of that attempt, for example `operation.status=TransactionTooLarge`.

What to do: nothing in the code. Expect the `operations.completed` rate of a write workload to drop
by half after the upgrade, without a change in the traffic.

## Fewer histogram buckets in the client metrics

If a dashboard or an alert reads a bound of `db.fdb.client.transactions.duration`,
`db.fdb.client.operations.duration` or `db.fdb.client.operations.size`, this section concerns you.

- `AddFoundationDbInstrumentation()` configures 10 bounds for the two duration histograms (1 ms to 5 s)
  and 9 bounds for the size histogram (100 B to 10 MB), instead of 18 and 20.
- Each exported point carries a count per bucket and can hold one exemplar per bucket, so the telemetry
  backend stores about half as much for these histograms.

What to do: check the queries that read a single bound. A query on a bound removed from the list, such
as `le="0.075"`, returns no data after the upgrade.

## A cancelled HTTP request returns while the server withholds its response

`BetterHttpClient` connections to a single endpoint (an IP address, for example) did not close their
socket when a request was cancelled. A cancelled request to a server that never answered did not
return. In 7.4.8, the cancelled request throws `OperationCanceledException`, and the server sees the
connection close.

What to do: nothing.

## Aspire starts the 7.4.10 cluster image

Under the `LatestMajor`, `LatestMinor` and `LatestPatch` version policies, `AddFoundationDb` starts the
7.4.10 image of a 7.4 cluster, instead of 7.4.8. A cluster that pins its version is unchanged.

## FakeDb: a cancelled commit leaves no conflict ranges

In `FoundationDB.FakeDb`, the conflict ranges of a cancelled commit stayed in the published snapshot.
In 7.4.8, a cancelled commit leaves no trace in it.

## FoundationDB.Aspire.Hosting requires MessagePack 3.1.12

`Aspire.Hosting` 13.6.1 depends on MessagePack 2.5.302, which has the advisory GHSA-qhrr-8q5h-9q3h.
`FoundationDB.Aspire.Hosting` 7.4.8 depends on MessagePack 3.1.12, the latest stable release, so an
AppHost that references it restores 3.1.12 instead of 2.5.302.

What to do: nothing.
