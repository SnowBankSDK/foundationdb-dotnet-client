# Migrating from 7.4.3 to 7.4.4

What changed for you between the `7.4.3` packages and `7.4.4`, and what you have to do about it.

> **This document is still being written.** 7.4.4 is not tagged yet, so entries are added as changes land.
> Anything already listed here has been verified against the shipped code.

Most applications upgrade by bumping the package version and rebuilding. The two sections you must read are
[Breaking changes](#breaking-changes) and [Behavior changes](#behavior-changes); the rest is informational.

## How to read this

| Section | What it means for you |
|---|---|
| [Breaking changes](#breaking-changes) | your code no longer compiles, or a required signature moved |
| [Behavior changes](#behavior-changes) | your code still compiles, but does something different at run time (often in the output) |
| [New APIs](#new-apis) | nothing to do, unless you want the feature |
| [Build and tooling](#build-and-tooling) | only if you build from source, or you run the test suites |

## Breaking changes

### `[CrystalJsonSerializable]` is obsolete, use `[CrystalSerializable]`

Enrolling a type in a source-generated container is now format-neutral: the same attribute serves every
output format the container requests (JSON, XML, or both), rather than one attribute per format. `[CrystalSerializable(typeof(...))]`
is the new spelling; `[CrystalJsonSerializableAttribute]` still compiles but is marked `[Obsolete]` (a `CS0618`
warning, not an error - nothing fails the build yet):

```csharp
// BEFORE (still compiles, now a CS0618 warning)
[CrystalJsonSerializable(typeof(Widget))]

// AFTER
[CrystalSerializable(typeof(Widget))]
```

The rename is mechanical: search for `CrystalJsonSerializable` and replace with `CrystalSerializable`. See
[New APIs](#new-apis) below for the full attribute model this belongs to, and
[`Documentation/CrystalXml.md`](../CrystalXml.md) for the complete truth table.

## Behavior changes

### Two IL-level shape changes behind the new attribute hierarchy

`CrystalJsonConverterAttribute` and `CrystalJsonSerializableAttribute` (formerly `CrystalJsonSerializable`) now
sit under the new format-neutral base classes:

- `CrystalJsonConverterAttribute` derived directly from `System.Attribute`; it now derives from
  `CrystalConverterAttribute`.
- `CrystalJsonSerializableAttribute` declared its own `Type[] Types { get; set; }` property; that property is
  now inherited from `CrystalSerializableAttribute`, and the attribute's own declaring type carries no `Types`
  member of its own.

**Both changes are source-compatible**: existing code that references either attribute, or reads `.Types`,
recompiles unchanged against the new version, and nothing in ordinary usage (attribute construction, property
access, the source generator's own `ForAttributeWithMetadataName` lookup, which matches by exact metadata name
regardless of the base type) is affected. The only population that can observe a difference is code doing its
own reflection over a **precompiled** assembly built against the old shape - for example, code that walks
`GetType().BaseType` expecting `System.Attribute` directly, or that looks up `Types` with
`BindingFlags.DeclaredOnly` expecting it on the attribute's own type rather than inherited. If you have such
code (most applications do not), recompile it against the new package rather than mixing binaries.

### `CJSON0013` no longer fires on `PropertyNameCaseInsensitive`

`CJSON0013` ("a format profile cannot be combined with a naming policy") refuses combining a format profile (for
example `DataContractCompat`) with a member-naming *policy* (camelCase and friends), because the profile's format
uses the declared member names and a naming policy would silently move them. `PropertyNameCaseInsensitive` is
not such a policy: it only relaxes how an **incoming** member name is matched while reading, and changes
nothing the profile **writes**. It is not a trigger for `CJSON0013`, on either the JSON side or its XML
counterpart `CXML0001`. If you previously routed around `CJSON0013` by dropping
`PropertyNameCaseInsensitive` on a compat container, you can restore it: strict on output, lenient on input.

### One nesting-depth cap for every serialization format: `CrystalJsonWriter.MaxDepth = 64`

The two JSON writers each carried their own private depth cap of 16 levels, the generated paths had none, and
the JSON parser refused past 64. All formats and the parser now share a single named constant,
`SnowBank.Data.Json.CrystalJsonWriter.MaxDepth = 64` (`CrystalXml.MaxDepth` is kept as an alias pointing at the
same constant). The value is the default maximum depth of both System.Text.Json and Newtonsoft.Json, so a
document this library writes stays readable by the mainstream .NET stacks at their defaults, and anything this
library writes it can read back. For the JSON writers this is **strictly a loosening** (64 up from 16): no
object graph that serialized successfully before can start failing. The generated paths, which previously had
no cap at all, now refuse past 64 with a typed exception instead of overflowing the stack.

## New APIs

### CrystalJson/CrystalXml: format-neutral container attributes and the output truth table

Declaring a source-generated container is now split into three independent concerns: which class hosts the
generated code (`[CrystalConverter]`), which format(s) it produces (`[CrystalJsonOutput]` and/or
`[CrystalXmlOutput]`), and which types it enrolls (`[CrystalSerializable(typeof(...))]`, format-neutral - the
enrolled type gets a generated serializer for every format the container requests).

```csharp
[CrystalConverter]
[CrystalJsonOutput(CrystalJsonSerializerDefaults.Web)]
[CrystalXmlOutput]
[CrystalSerializable(typeof(User))]
[CrystalSerializable(typeof(Product))]
public static partial class ApplicationSerializers
{
    // generated code will be inserted here
}
```

`[CrystalJsonConverter]` and `[CrystalXmlConverter]` remain as mono-format aliases (marker + a single output
format bundled together) for the common case of a container that only ever produces one format. A container
combining an alias with an explicit output attribute, one that names no output format at all, or one carrying
several container markers, is refused at build time - see [Diagnostics](#diagnostics-reference) below.

`CrystalOutputAttribute` is the (non-generated-code-visible) common base of `[CrystalJsonOutput]` and
`[CrystalXmlOutput]`, kept purely for documentation and discoverability: the source generator matches each
output attribute by its exact metadata name, not by walking this hierarchy, so a type derived from
`CrystalConverterAttribute`, `CrystalOutputAttribute`, or `CrystalSerializableAttribute` is invisible to it and
does not enroll as a recognized format or container marker. Do not subclass any of the three.

The full truth table, the execution pipeline, the compat (`DataContract`) and modern XML profiles, and every
diagnostic in detail are documented in [`Documentation/CrystalXml.md`](../CrystalXml.md); this entry only
summarizes what changed relative to 7.4.3.

### Diagnostics reference

One line each, for the diagnostics introduced or reshaped by this release:

| Diagnostic | Severity | Meaning |
|---|---|---|
| `CRYS0001` | Error | `[CrystalConverter]` names no output format; the container would generate nothing |
| `CRYS0002` | Error | A mono-format alias (`[CrystalJsonConverter]`/`[CrystalXmlConverter]`) is combined with an output attribute, which the alias cannot express |
| `CRYS0003` | Error | A container carries several container markers, which is two answers to "what does this container produce" |
| `CJSON0019` | Warning | A `[CrystalSerializable]` enrollment names a type CrystalJson already serializes natively; no converter is generated for it |
| `CJSON0020` | Info | The generated JSON proxy surface (`ToReadOnly`/`ToMutable`, the proxy types) is skipped because the compilation is below .NET 7+/C# 11; the converter, `TypeMapper`, and any requested XML output are unaffected |
| `CXML0001` – `CXML0013` | mostly Error, `CXML0012` Info | The XML-specific rules (DataContract format vs naming policy, missing serializer container, invalid attribute projections, name collisions, missing inner-item names, invalid XML names, converters without an XML facet, `[CollectionDataContract]` not honored on the DataContract format, dictionary shapes with no lexical form, inert settings, and the get-only `[DataMember]` property that the compat format refuses) - see `Documentation/CrystalXml.md` for the full table |

## Build and tooling

Only relevant if you build the SDK from source, consume it as a submodule, or run its test suites.

- **The XML certification suite now runs on the net472 validation target as well**, alongside the existing
  netstandard2.0 build check: the lite path is exercised on the real .NET Framework CLR for XML output exactly
  as it already was for JSON.
- **Generated code for an XML-only container compiles on the lite (netstandard2.0/net472) consumer.** No
  language or runtime feature specific to XML emission requires more than the generator's existing floor.

## Nothing to do

Recorded so you can tell "no entry" from "not looked at":

- The public `FoundationDB.Client` transaction, key, subspace and directory APIs are unchanged in 7.4.4.
- Existing JSON-only containers (`[CrystalJsonConverter]`, or `[CrystalConverter]` + `[CrystalJsonOutput]`)
  generate exactly what they generated in 7.4.3; nothing about the JSON format itself moved.
