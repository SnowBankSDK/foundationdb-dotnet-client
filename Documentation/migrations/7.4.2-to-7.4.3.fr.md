# Migrer de 7.4.2 vers 7.4.3

Ce qui change pour vous entre les *packages* `7.4.2` et `7.4.3`, et ce que vous avez à faire.

La plupart des applications se mettent à jour en montant la version du *package* et en recompilant. Les deux sections à lire absolument sont [Changements cassants](#changements-cassants) et [Changements de comportement](#changements-de-comportement) ; le reste est informatif.

## Comment lire ce document

| Section | Ce que ça signifie pour vous |
|---|---|
| [Changements cassants](#changements-cassants) | votre code ne compile plus, ou une signature requise a bougé |
| [Changements de comportement](#changements-de-comportement) | votre code compile toujours, mais fait autre chose à l'exécution (souvent sur le fil) |
| [Nouvelles API](#nouvelles-api) | rien à faire, sauf si vous voulez la fonctionnalité |
| [*Build* et outillage](#build-et-outillage) | seulement si vous buildez depuis les sources, ou si vous lancez les suites de tests |

## Changements cassants

### `TokenMap` et `TokenDictionary` sont désormais des erreurs de compilation sur net9+

`TokenMap<T>`, `ByteStringTokenMap`, `CharStringTokenMap` et le type de stockage `TokenDictionary` étaient déjà marqués `[Obsolete]` sur net9+ dans les versions précédentes. Les six attributs sont maintenant `[Obsolete(error: true)]`, donc tout usage restant fait échouer le *build*.

```csharp
// AVANT (avertissement sur net9+)
var map = new CharStringTokenMap();

// APRÈS : utilisez l'alternate lookup de la BCL
var lookup = dictionary.GetAlternateLookup<ReadOnlySpan<char>>();
```

Les types restent utilisables sur `net8.0`, `netstandard2.0` et `net472`, qui n'ont pas d'équivalent `AlternateLookup`. Le retrait est un mouvement pour la prochaine version majeure, pas pour une 7.4.x.

### Les *generated converters* respectent désormais `[JsonIgnore]`

C'est un **changement de fil** pour quiconque utilise la génération de source `[CrystalJsonConverter]` sur un type qui porte un `[JsonIgnore]`, l'orthographe `System.Text.Json` ou celle de Newtonsoft (JSON.NET). Jusqu'à 7.4.2, le générateur ne reconnaissait ni l'un ni l'autre et sérialisait le membre quand même, alors que la *reflection path* l'avait toujours exclu (en reconnaissant `[JsonIgnore]` par son nom, quel que soit le namespace) sur un type **sans** `[DataContract]` (sur un type `[DataContract]`, la *reflection path* a son propre changement, section suivante). Les deux chemins concordent désormais, pour les deux orthographes.

```csharp
[JsonIgnore] public string Secret { get; set; }                  // generated converter 7.4.2 : émis. 7.4.3 : absent.
[Newtonsoft.Json.JsonIgnore] public string Legacy { get; set; }  // idem, l'orthographe JSON.NET est respectée en 7.4.3
```

Si un consommateur de votre *generated converter* dépendait de la présence de ce membre, retirez l'attribut ou donnez-lui une condition explicite (ci-dessous).

Les membres sont aussi retirés des *generated proxies*, pas seulement de la sérialisation, donc `MyJson.Widget.ReadOnly.Secret` disparaît aussi de la surface générée.

### Un `[JsonIgnore]` inconditionnel à côté d'un signal d'inclusion est désormais refusé, bruyamment

Un membre portant un `[JsonIgnore]` **inconditionnel** (pas de `Condition`, ou `Condition = Always`, ou l'orthographe JSON.NET) à côté d'un **signal d'inclusion** (`[DataMember]`, `[JsonInclude]`, ou un attribut de nommage de type `[JsonProperty]`) est refusé sur les deux chemins : la *reflection path* **lève une exception au moment de construire le contrat du type** (une fois, mise en cache, dans les deux sens), et le générateur de source signale l'**erreur `CJSON0008`** à l'emplacement du membre. C'est un changement de comportement délibéré : la combinaison se résolvait auparavant **silencieusement**, et la manière dont elle se résolvait changeait d'une version à l'autre, ce qui est exactement le genre de mouvement de fil silencieux que cette version refuse partout ailleurs :

| Version | Membre avec `[DataMember]` + `[JsonIgnore]` inconditionnel, *reflection path* |
|---|---|
| 7.4.2 | **inclus** (la porte d'opt-in `[DataMember]` s'exécutait avant la vérification `[JsonIgnore]`) |
| 7.4.3-rc.1 | **exclu, dans les deux sens**, sans diagnostic |
| 7.4.3 | **refusé bruyamment** (exception à la construction du contrat ; le générateur émet une erreur) |

La population qui écrit les deux attributs est le **DTO à double sortie** : le fil d'un sérialiseur portait le membre (`[DataMember]`, ou un renommage `[JsonProperty]`), celui de l'autre non (`[JsonIgnore]`). Un DTO à double sortie n'est pas supporté, et ne le sera pas : **le remède est la scission, un DTO par sérialiseur, chacun avec un unique jeu d'attributs cohérent** (le même cadrage que le refus des « deux noms de fil différents », qui est le même défaut à travers les attributs de nommage). Si la paire est simplement une bévue sur un DTO normal à sortie unique, retirez l'un des deux attributs ; lequel dépend de quelle intention était réelle. Ne « corrigez » **pas** l'erreur en donnant une `Condition` au `[JsonIgnore]` : une `Condition` transforme le membre en membre *inclus* avec une règle d'écriture, donc l'erreur de *build* disparaît pendant que le membre part sur le second fil pour la première fois.

Un `[JsonIgnore(Condition = ...)]` conditionnel reste légal partout, y compris à côté de `[DataMember]` : c'est la recette `EmitDefaultValue=false`, et elle ne change jamais l'appartenance.

**Note de dimensionnement pour les mises à jour** : le refus couvre aussi la paire de style Newtonsoft (`[JsonProperty]` + `[JsonIgnore]`), donc une *codebase* fortement Newtonsoft devrait mesurer cette population *avant* de mettre à jour : chacun de ces membres devient une erreur de *build* ou de construction de contrat, pas une suppression silencieuse.

### Un membre qui déclare deux noms de fil différents pour deux sérialiseurs est refusé

Un membre portant plus d'un attribut de nommage avec un nom **différent** est un seul type qui essaie de servir deux contrats de fil à la fois : quel que soit le nom qu'un sérialiseur choisit, l'un des deux consommateurs reçoit le mauvais document. Cela couvre `[DataMember(Name = "x")]` contre un attribut de nommage JSON, et les trois attributs de nommage JSON entre eux : CrystalJson `[JsonProperty("x")]`, System.Text.Json `[JsonPropertyName("y")]`, et Newtonsoft `[JsonProperty("z")]`. La *reflection path* lève une exception à la construction du contrat, en nommant le membre, les deux attributs et les deux noms ; le générateur de source signale l'**erreur `CJSON0011`** au niveau du membre. Les deux sens refusent, puisque la lecture et l'écriture partagent le contrat.

```csharp
[DataMember(Name = "id"), JsonProperty("identifier")]        // 7.4.2 : un nom l'emportait silencieusement. 7.4.3 : refusé.
public string? Id { get; set; }

[JsonProperty("A"), Newtonsoft.Json.JsonProperty("B")]       // aussi refusé : deux noms JSON sur un seul membre
public string? Code { get; set; }
```

Un nom Newtonsoft `[JsonProperty]` **seul** est désormais respecté sur les deux chemins : le *generated converter* l'a appris en 7.4.3, et la *reflection path* l'utilisait déjà, donc les deux routes produisent le même fil (7.4.2 générait le nom brut du membre, en ignorant l'attribut). Quand plusieurs attributs de nommage sont présents et concordent, le nom effectif vient de celui de plus haute priorité, CrystalJson `[JsonProperty]` puis `[JsonPropertyName]` puis Newtonsoft `[JsonProperty]` ; un désaccord entre eux est le refus ci-dessus. Le remède pour un vrai conflit est la même scission que pour le refus `[JsonIgnore]` : un DTO par sérialiseur, chacun avec un unique jeu d'attributs cohérent.

### Un type `[DataContract]` enrôlé dans un *container* généré reçoit désormais le fil DataContract

Jusqu'à cette version, le générateur acceptait un tel type et ignorait silencieusement ses attributs DataContract : tous les membres publics, noms C#. Cela produisait un **fil différent de la *reflection path***, qui respecte l'opt-in `[DataMember]`, les renommages, `IsRequired`, et les membres non publics. Deux fils pour le même type, choisis selon le chemin qui l'a sérialisé, est exactement la divergence silencieuse que cette version refuse partout ailleurs.

Les *generated converters* implémentent désormais le modèle d'appartenance DataContract, donc les deux chemins concordent :

```csharp
[DataContract]
public sealed class Order
{
    [DataMember(Name = "id")]          public string? Id { get; set; }
    [DataMember(Name = "total")]       private decimal Total { get; set; }   // non-public : inclus
    public string? Scratch { get; set; }                                     // pas de [DataMember] : exclu
}
```

```json
// 7.4.2 généré : {"Id":null,"Scratch":null}      <- attributs DataContract ignorés
// 7.4.3 généré : {"id":null,"total":0}           <- identique à la reflection path
```

Ce que le chemin généré applique : `[DataMember]` comme seul opt-in d'appartenance (un membre public sans lui est **exclu**), les renommages `Name=`, les membres et accesseurs non publics (atteints via des *accessor thunks*), et `IsRequired = true` (un membre absent lève une exception à la lecture ; un `null` explicite le satisfait, comme le fait `DataContractJsonSerializer`). `Order=` et `EmitDefaultValue=` ne sont lus sur aucun des deux chemins.

**L'ordre des membres est l'ordre de déclaration, et il ne correspond pas à DCJS.** `DataContractJsonSerializer` émet d'abord les membres qui ne portent pas de `Order=`, par ordre alphabétique de leur nom de fil, puis ceux portant `[DataMember(Order = n)]` par `n` croissant. Cette bibliothèque émet l'ordre de déclaration, sur la *reflection path* comme dans les *generated converters*. La différence est invisible pour tout lecteur JSON conforme, puisque les membres d'un objet sont non ordonnés par définition, et elle est visible pour tout ce qui compare les octets : un diff *golden-file* contre une réponse *legacy* capturée, un hash ou un checksum sur la charge utile, ou une déduplication adressée par contenu. Si vous avez besoin que les octets correspondent, réordonnez les déclarations ; aucun réglage ne restaure l'ordre DCJS.

**C'est un changement de fil pour tout type déjà enrôlé**, dans le sens de la *reflection path*. Si vous vous appuyiez sur l'ancienne sortie tout-public/noms-C#, ce fil reste atteignable exprès : retirez les attributs DataContract du type, ou détachez un DTO simple, l'un ou l'autre rendant l'intention explicite plutôt qu'un accident du chemin.

Un type `[DataContract]` simplement *référencé* par un membre d'un DTO enrôlé a toujours été correct et l'est toujours : dans le code généré il passe par le *runtime resolver*, qui applique le même modèle.

### `[CrystalJsonSerializable]` est obsolète, utilisez `[CrystalSerializable]`

Enrôler un type dans un *container* généré à la source est désormais neutre en format : le même attribut sert chaque format de sortie que le *container* demande (JSON, XML, ou les deux), plutôt qu'un attribut par format. `[CrystalSerializable(typeof(...))]` est la nouvelle orthographe ; `[CrystalJsonSerializableAttribute]` compile toujours mais est marqué `[Obsolete]` (un avertissement `CS0618`, pas une erreur, rien ne fait encore échouer le *build*) :

```csharp
// AVANT (compile toujours, désormais un avertissement CS0618)
[CrystalJsonSerializable(typeof(Widget))]

// APRÈS
[CrystalSerializable(typeof(Widget))]
```

Le renommage est mécanique : cherchez `CrystalJsonSerializable` et remplacez par `CrystalSerializable`. Voir [Nouvelles API](#nouvelles-api) ci-dessous pour le modèle d'attributs complet auquel cela appartient, et [`Documentation/CrystalXml.md`](../CrystalXml.md) pour la table de vérité complète.

### `IJsonPacker<T>.Pack` prend un `ref CrystalJsonPackContext`

Le seul membre de l'interface passe de `Pack(T instance, CrystalJsonSettings? settings = null, ICrystalJsonTypeResolver? resolver = null)` à `Pack(ref CrystalJsonPackContext context, T instance)`. Le contexte porte les settings, le resolver, la profondeur d'imbrication, et la pile des objets visités de tout le parcours de packing, par ref à travers chaque appel imbriqué, y compris les helpers de pack de collection/dictionnaire. Avant, ces helpers ne pouvaient appeler que le membre à trois arguments, donc les gardes de récursion se réinitialisaient à chaque frontière de collection et un cycle de références passant par un membre `List<T>` faisait crasher le processus sur un `StackOverflowException` ; maintenant il lève la même erreur de récursion attrapable que tous les autres chemins.

Qui est concerné, et que faire :

- **Le code qui appelle `Pack(instance, settings, resolver)`** continue de compiler et se comporte à l'identique : cette forme survit comme méthode d'extension qui ouvre un contexte neuf et le transmet.
- **Les *containers* générés à la source** prennent la nouvelle forme en recompilant ; rien à éditer.
- **Les implémentations `IJsonPacker<T>` écrites à la main** (convertisseurs personnalisés nommés dans `[JsonConvertWith(...)]`) doivent changer leur signature en `Pack(ref CrystalJsonPackContext context, T instance)` ; lisez les settings et le resolver depuis le contexte. Un convertisseur qui packe des valeurs imbriquées passe le même contexte plus loin.
- Les assemblies précompilées buildées contre l'ancienne interface doivent être recompilées ; ne mélangez pas les binaires à travers ce changement.

### `CrystalJsonSettings.OptionFlags.EnumsAsString` est désormais une erreur de compilation

Le bit de flag est renommé `EnumsAsNumbers`, avec le sens opposé, parce que la forme de fil par défaut des enums est passée aux chaînes (voir [Changements de comportement](#changements-de-comportement)). L'ancien membre survit en `[Obsolete(error: true)]`, donc l'échec de *build* nomme le remplacement. La propriété booléenne `EnumsAsString` et les méthodes fluent `WithEnumAsStrings()` / `WithEnumAsNumbers()` gardent leurs noms et leur sémantique. Seul le code qui manipule directement `OptionFlags` est concerné.

### `IFdbDatabase.BeginTransactionAsync` est désormais une erreur de compilation

Le `BeginTransactionAsync(FdbTransactionMode, CancellationToken, FdbOperationContext?)` à trois arguments portait `[Obsolete]` en avertissement en 7.4.2 et porte maintenant `[Obsolete(..., error: true)]`. Le membre est toujours là, donc le *build* échoue avec un message nommant le remplacement plutôt qu'avec un membre manquant.

Appelez `BeginTransaction(...)` à la place. La surcharge est `[EditorBrowsable(Never)]` depuis un certain temps, donc un site d'appel survivant est antérieur à cela.

## Changements de comportement

### `[JsonIgnore(Condition = ...)]` suit la sémantique System.Text.Json

La *reflection path* et le générateur de source lisent désormais la propriété `Condition` au lieu de traiter tout `[JsonIgnore]` comme une exclusion inconditionnelle.

| Condition | 7.4.2 | 7.4.3 |
|---|---|---|
| `Always` (la valeur par défaut) | exclu | exclu (inchangé) |
| `Never` | exclu | **toujours émis**, l'emportant sur les rejets null/défaut au niveau des settings |
| `WhenWritingNull` | exclu | omis seulement quand la valeur est null |
| `WhenWritingDefault` | exclu | omis seulement quand la valeur égale la valeur par défaut du membre |

Notez le piège de nommage System.Text.Json : `JsonIgnoreCondition.Never` signifie « ne jamais ignorer ce membre ».

Deux divergences délibérées par rapport à System.Text.Json : `WhenWritingDefault` compare à la valeur par défaut *déclarée* du membre (donc `[JsonProperty(DefaultValue = ...)]` se compose avec elle) plutôt qu'à `default(T)` toujours, et `WhenWritingNull` sur un value type non nullable est inerte au lieu de lever une exception.

Un attribut sans propriété `Condition` (par exemple le `[JsonIgnore]` de JSON.NET) compte comme inconditionnel, et un ignore inconditionnel est vérifié **avant** la porte d'opt-in `[DataContract]`, donc il exclut le membre même à côté d'un `[DataMember]` (voir le changement cassant ci-dessus). Ce que la porte `[DataMember]` court-circuite, ce sont les filtres qui s'exécutent après elle (`[IgnoreDataMember]`, le *name matching* de style JSON.NET). Un `[JsonIgnore(Condition = ...)]` **conditionnel** ne change jamais l'appartenance : il enregistre la règle d'émission par membre et retombe sur la porte `[DataMember]`, ce qui explique pourquoi `[DataMember(EmitDefaultValue = false)]` + `[JsonIgnore(Condition = WhenWritingDefault)]` fonctionne sur un type `[DataContract]`.

### Membres non publics : `[DataMember]` suffit sur un type `[DataContract]`, `[JsonInclude]` partout ailleurs

**C'est un changement de fil pour les types `[DataContract]`, énoncé bruyamment parce que des membres APPARAISSENT dans la sortie.** La règle est hybride, par décision :

- **Sur un type `[DataContract]`, `[DataMember]` sur un membre non public est respecté automatiquement** par la *reflection path* : les champs et propriétés privés, internal et protected sérialisent et bindent, et les accesseurs non publics d'une propriété `[DataMember]` publique (par exemple un setter privé) sont utilisables pour la désérialisation. C'est la fidélité à `DataContractJsonSerializer` : le modèle DataContract est aveugle à l'accessibilité par définition, et la paire d'attributs est déjà la déclaration explicite de l'intention. Un DTO dont les membres `[DataMember]` non publics étaient silencieusement supprimés par CrystalJson produit désormais la même appartenance que DCJS. Si un consommateur s'appuyait sur l'absence de ces membres dans la sortie de CrystalJson, ce fil change avec cette version.
- **Sur un type sans `[DataContract]`**, les membres non publics restent invisibles sauf s'ils sont annotés avec le `[JsonInclude]` de `System.Text.Json`, inchangé (et délibérément un surensemble de System.Text.Json, dont le sérialiseur par réflexion rejette les membres non publics). Un `[DataMember]` sur un membre privé d'un POCO ne fait rien, exactement comme il ne faisait rien sous DCJS.
- `[JsonInclude]` seul n'accorde toujours aucune appartenance sur un type `[DataContract]` : `[DataMember]` est l'opt-in là, comme DCJS l'a défini. Là où vous avez ajouté `[JsonInclude]` à côté de `[DataMember]` comme opt-in provisoire, il continue de fonctionner et est maintenant simplement redondant.

Le générateur de source suit pour `[JsonInclude]` : un membre non public (ou l'accesseur non public d'une propriété publique) portant l'attribut est atteint via des ***accessor thunks*** : des thunks `[UnsafeAccessor]` sans coût quand la cible consommatrice définit l'attribut (net8+), des accesseurs par réflexion sinon (fil correct, plus lent ; un repli, jamais un refus). **`SYSLIB1038` est retiré** : le générateur n'omet plus de tels membres. Un résidu délibéré : un membre `internal` SANS aucun signal d'inclusion/exclusion garde son inclusion historique générée seulement (des fils générés existants en dépendent) et reçoit maintenant l'avertissement supprimable **`CJSON0012`**, qui pousse vers un `[JsonInclude]` explicite (inclus sur les deux chemins) ou `[JsonIgnore]` (exclu sur les deux) ; voir [*Build* et outillage](#build-et-outillage). L'appartenance pilotée par `[DataMember]` dans les *containers* générés arrive aussi dans cette version (voir le changement cassant ci-dessus), et elle a priorité sur un type `[DataContract]` : là, `[DataMember]` est le seul signal d'appartenance et l'accessibilité ne filtre pas, donc ce résidu du membre `internal` ne s'applique pas.

### `[IgnoreDataMember]` exclut désormais le membre

7.4.2 ne lisait jamais l'attribut ; le membre sérialisait quand même. Les deux chemins le respectent maintenant : sur un type sans `[DataContract]`, un membre portant `[IgnoreDataMember]` disparaît du fil à l'écriture et est sauté à la lecture. **C'est un changement de fil pour tout POCO qui portait déjà l'attribut.**

Sur un type `[DataContract]` l'attribut reste inerte, parce que la porte d'opt-in `[DataMember]` s'exécute en premier. C'est la fidélité à `DataContractJsonSerializer` : DCJS ignore aussi `[IgnoreDataMember]` sur un type `[DataContract]`.

### Les orthographes étrangères de `[JsonConverter(typeof(...))]` sont respectées

Un membre ou un type portant le `[JsonConverter(typeof(X))]` de System.Text.Json ou de JSON.NET sérialise désormais à travers `X`, **quand `X` implémente le contrat de convertisseur CrystalJson** (`IJsonPacker<T>` et/ou `IJsonDeserializer<T>` pour le type de la valeur). 7.4.2 ignorait l'attribut entièrement, donc c'est un changement de fil pour tout DTO dont cette bibliothèque sait exécuter le convertisseur nommé. Un type de convertisseur qu'elle ne sait pas exécuter continue d'être ignoré, délibérément : un DTO à moitié migré dont le convertisseur ne parle que System.Text.Json reste sérialisable avec le traitement par défaut.

Un convertisseur qui n'existe que pour CrystalJson a sa place sur l'attribut natif à la place : voir l'entrée `[JsonConvertWith]` sous [Nouvelles API](#nouvelles-api).

### Les membres requis sont vérifiés à la lecture par la *reflection path*

Deux changements liés, tous deux levant `JsonBindingException` là où un bind réussissait silencieusement auparavant :

- **Les membres C# `required`** (non nullables) : un membre null-ou-manquant lève désormais une exception sur la *reflection path*, le même contrat que le chemin généré à la source a toujours imposé (« Required JSON field ... was null or missing »). Jusqu'à présent la *reflection path* enregistrait le flag et bindait le membre à sa valeur par défaut sans broncher, donc les deux chemins étaient en désaccord sur le même DTO.
- **`[DataMember(IsRequired = true)]` sur un type `[DataContract]`** : un membre ABSENT du document lève désormais une exception à la lecture, fidèle à DCJS ; un **`null` explicite le satisfait**, délibérément distinct du `required` C#, où null refuse aussi. Le côté écriture est inchangé (`WithNullMembers()` reste la recette pour alimenter un lecteur *legacy* figé, qui lève une exception sur le null omis de SON côté).

Si une population de documents stockés manque légitimement de tels membres, la correction est sur le type (retirez `required`, ou `IsRequired = false`), pas sur le lecteur : les flags signifient maintenant ce qu'ils disent.

### Les dictionnaires bindent depuis la forme *array* DataContract *legacy*

`DataContractJsonSerializer` sérialise `IDictionary<K, V>` comme un tableau d'objets `{"Key":..,"Value":..}`. Les binders de dictionnaire acceptent désormais cette forme à la lecture, dans la branche qui levait toujours une exception auparavant.

```json
[ { "Key": "a", "Value": 1 }, { "Key": "b", "Value": 2 } ]   // 7.4.2 : JsonBindingException. 7.4.3 : binde.
```

Le *fast path* object-map est intact et aucune entrée qui fonctionnait avant ne change de sens. Le lecteur est strict par conception : chaque élément doit être un objet avec exactement les deux membres `Key` et `Value` (casse exacte), et un seul élément non conforme fait échouer tout le bind avec un `JsonBindingException` nommant son index. Un tableau vide binde vers un dictionnaire vide. Les *generated converters* en héritent gratuitement, puisque leurs lectures de dictionnaire passent par les mêmes binders à l'exécution.

Les types de dictionnaire sans binder personnalisé (par exemple `ImmutableDictionary`) rejettent toujours la forme *legacy*.

### Les types de collection *legacy*/BCL bindent au lieu de lever une exception, ou de binder faux

Un balayage systématique des catégories de collection que le corpus de l'ère DCJS et la matrice de support System.Text.Json exercent, avec une règle : chaque type soit fait un *round-trip* correct, soit échoue bruyamment avec un message actionnable. Ce qui a changé à la lecture :

| Type déclaré | 7.4.2 | 7.4.3 |
|---|---|---|
| `Queue<T>`, `ConcurrentQueue<T>` | pas de binder, `JsonBindingException` | binde ; l'ordre du fil est l'ordre de défilement |
| `Stack<T>`, `ConcurrentStack<T>` | pas de binder | binde ; le *round-trip* préserve le fil (les sérialiseurs *legacy* inversaient une pile à chaque passage) |
| `ConcurrentBag<T>` | pas de binder | binde ; contenu préservé, ordre non spécifié |
| `ImmutableSortedSet<T>` | tombait dans le fourre-tout `IImmutableSet<>` et recevait un `ImmutableHashSet<T>`, non assignable au type déclaré : null silencieux | binder dédié, type correct |
| `IReadOnlySet<T>` | recevait un `ReadOnlyCollection<T>` qui n'implémente pas l'interface | binde vers `HashSet<T>` |
| `IDictionary<K,V>`, `IReadOnlyDictionary<K,V>` comme types déclarés | pas de binder | bindent vers `Dictionary<K,V>` |

Les sous-classes de `Collection<T>` (et les sous-classes de collection utilisateur en général) bindent aussi vers le type **déclaré** au lieu d'une forme de base, et le générateur de source ne produit plus de convertisseurs invalides pour elles.

Rien de ce qui bindait correctement en 7.4.2 ne change de sens : les changements transforment des refus et des formes fausses silencieuses en binds fonctionnels.

### Les enums sérialisent en chaînes par défaut, sur chaque route

La forme de fil par défaut d'un enum passe de la valeur numérique au littéral chaîne, sur le *text writer*, la route DOM et les *generated converters* pareillement :

```csharp
enum Status { Active = 2 }
// 7.4.2: {"status":2}
// 7.4.3: {"status":"Active"}
```

C'est une divergence délibérée par rapport à System.Text.Json : les enums en chaînes gardent les charges utiles autodescriptives et se lisent naturellement depuis les clients JavaScript. **La lecture est inchangée et tolérante dans les deux sens** : les noms et les tokens personnalisés bindent sans tenir compte de la casse, et les nombres et chaînes numériques sont toujours acceptés. Les charges utiles préexistantes se désérialisent sans aucun changement, et une flotte mixte peut avancer de façon incrémentale.

Pour garder le fil numérique : `WithEnumAsNumbers()` sur les settings, ou `[JsonProperty(EnumFormat = JsonEnumFormat.Number)]` par membre, respecté sur les deux chemins et sur la route DOM. La parité d'octets `DataContractJsonSerializer` exige la forme numérique ; le preset `DataContractCompat` ([Nouvelles API](#nouvelles-api)) la sélectionne déjà. L'ancien bit `OptionFlags.EnumsAsString` est retiré, voir [Changements cassants](#changements-cassants).

### `[JsonBooleanLiterals]` prend un seul constructeur, et un littéral false null signifie « ne pas émettre »

Les deux constructeurs typés (`string, string` et `int, int`) sont remplacés par un unique `JsonBooleanLiteralsAttribute(object? whenFalse, object whenTrue)`. **C'est une cassure binaire contre 7.4.3-rc.1, et c'est source-compatible** : `[JsonBooleanLiterals("0", "1")]` et `[JsonBooleanLiterals(0, 1)]` compilent tous deux inchangés contre le nouveau constructeur, donc les consommateurs recompilent et passent à autre chose. Trois constructeurs ne pouvaient pas coexister, parce que `[JsonBooleanLiterals(null, "1")]` se lie à la surcharge typée `(string, string)` et échoue là avant que la surcharge `object` ne soit jamais considérée.

Ce que le constructeur unique apporte, c'est un premier argument **null**, signifiant que le membre n'est pas émis du tout quand la valeur est false :

```csharp
[JsonBooleanLiterals(null, "1")]    // true -> "1",  false -> membre absent
[JsonBooleanLiterals(null, true)]   // true -> true, false -> membre absent
```

Le second est l'idiome pour « émettre true, ou n'émettre rien » : le fil reste un booléen JSON ordinaire et la seule chose que l'attribut change est l'omission. C'est exactement équivalent à `[JsonBooleanLiterals("0","1")]` plus `[JsonIgnore(Condition = JsonIgnoreCondition.WhenWritingDefault)]`, et un test épingle les deux orthographes octet-identiques. `[JsonIgnore(Condition = ...)]` reste le mécanisme général pour tout autre type de membre ; ceci est l'orthographe spécifique au booléen qui énonce l'intention.

Les arguments acceptent une chaîne, un bool, ou une valeur numérique, et les deux n'ont pas à correspondre. Comme ils sont typés `object`, le compilateur ne les vérifie plus, donc les deux chemins le font : la *reflection path* lève une exception à la construction du contrat et le générateur signale **`CJSON0017`**, avec le même message.

Une combinaison se contredit et avertit. `StrictLiterals = true` rejette les vrais `true`/`false` JSON au profit des littéraux configurés, mais quand le littéral false est null il n'y a rien du côté false à imposer, parce que l'absence est ce qui porte false. Le générateur signale **`CJSON0018`** au niveau du membre, comme avertissement supprimable :

```csharp
[JsonBooleanLiterals(null, "1", StrictLiterals = true)]   // CJSON0018
```

Retirez `StrictLiterals`, ou donnez au membre un vrai littéral false. Les deux arguments sont connus à la compilation, donc la contradiction est signalée là où elle est écrite plutôt que découverte sur une charge utile.

### Les callbacks de cycle de vie s'exécutent désormais, et le paramètre `StreamingContext` est refusé

Les quatre callbacks `[OnSerializing]` / `[OnSerialized]` / `[OnDeserializing]` / `[OnDeserialized]` n'étaient jamais invoqués avant cette version. Ils sont invoqués maintenant, sur les deux routes d'écriture et à la lecture, donc un patrimoine `DataContractJsonSerializer` porté garde le comportement qu'il avait.

**Où ils se déclenchent**, à l'identique sur la *reflection path* et dans les *generated converters* (épinglé par un test qui fait passer le même type par les deux et compare) : `[OnSerializing]` strictement avant que le premier membre soit écrit et `[OnSerialized]` strictement après le dernier, sur les deux routes d'écriture ; `[OnDeserializing]` sur une instance construite mais non peuplée, `[OnDeserialized]` sur celle entièrement peuplée. Les convertisseurs de membre s'exécutent à l'intérieur de cette parenthèse.

**Les proxies n'ont pas de cycle de vie.** Un proxy read-only ou writable est une vue *lazy* sur le JSON : rien n'est construit et rien n'est peuplé, donc il n'y a pas d'intervalle qu'une paire pré/post puisse parenthéser. Les callbacks s'exécutent quand une valeur est **matérialisée** (`ToValue()`, `Deserialize`, `Unpack`). Si votre portage a adopté le « rester sur le proxy » comme principe, un callback ne s'exécutera pas pour vous jusqu'à ce que quelque chose demande la valeur. Un type dont les invariants dépendent d'un callback doit être lu comme une valeur, pas vu à travers un proxy.

**Seules les signatures modernes sont acceptées.** `void M(StreamingContext)`, la signature que DCJS exige, est refusée : le générateur signale **`CJSON0015`** au niveau du site d'appel, et la *reflection path* lève le même message quand elle construit le contrat du type. Les deux produisent ce texte, que vous pouvez grepper dans un journal de *build* :

```
Remove the StreamingContext parameter from serialization callback '<name>', or replace it with JsonValue,
JsonObject or JsonArray. The legacy DataContractJsonSerializer callback signature is not supported.
```

C'est un changement cassant délibéré et limité : la source-compatibilité est gardée partout où c'est possible, et les cassures sont acceptées là où la correction est triviale. Celle-ci est un chercher-remplacer sur les sites d'appel.

#### La recette du balayage

**Précondition, à vérifier avant de changer quoi que ce soit.** DCJS *exige* le paramètre `StreamingContext` et refuse `void M()` aussi fermement que nous refusons le paramètre. Donc convertir un callback **coûte à ce type sa compatibilité DCJS**. Un type doit par conséquent être converti en même temps que chaque service qui le sérialise. Si un DTO est partagé entre un service converti et un autre qui tourne encore sur DCJS, ils bougent ensemble ou pas du tout. Établissez d'abord quels types sont encore atteignables depuis un endpoint DCJS ; ne commencez pas le balayage tant que cette liste n'est pas vide pour les types que vous comptez convertir.

Ensuite, par type :

1. Trouvez les callbacks : cherchez `[OnSerializing]`, `[OnSerialized]`, `[OnDeserializing]`, `[OnDeserialized]`, puis prenez la méthode sur laquelle chacun se trouve.
2. Chaque méthode de ce genre a exactement deux issues légales :
   - **Retirer le paramètre**, donnant `void M()`. C'est le choix par défaut ; prenez-le chaque fois que le corps n'utilise pas `context`.
   - **Remplacer le paramètre** par `JsonValue`, `JsonObject` ou `JsonArray`, donnant par exemple `void M(JsonObject document)`. Ne prenez ceci que sur `[OnDeserializing]` / `[OnDeserialized]`, et seulement quand le callback a besoin d'inspecter la charge utile entrante. Le paramètre reçoit alors le document en cours de bind, qui est une capacité que DCJS n'a jamais eue. Choisissez `JsonObject` sauf si le type binde depuis un tableau.
3. Supprimez tout usage restant de la valeur `context` dans le corps. Elle ne portait aucune information que ce sérialiseur fournit.
4. Rebuildez. Tout site d'appel que vous avez manqué est une erreur de *build* portant le texte ci-dessus.

Ne passez pas `null` pour le paramètre afin de garder l'ancienne signature compilable : le callback peut le déréférencer, et un `NullReferenceException` est une mauvaise façon de le découvrir.

#### `[OnDeserializing]` et les membres `required` / `init`-only ne peuvent pas partager un type

C'est la deuxième erreur que le balayage rencontre, et contrairement à la première la correction est un choix de conception plutôt qu'une édition mécanique, donc il vaut la peine de la connaître avant de commencer.

Un callback de pré-peuplement doit observer une instance **construite mais non peuplée**. Le code généré construit donc d'abord et assigne les membres après, sous forme d'instructions. Un membre `required` ne peut être défini que dans un initialiseur d'objet, et un membre `init`-only de même, donc ni l'un ni l'autre ne peut être assigné de cette façon. Le générateur signale **`CJSON0016`** sur le type, en nommant le membre fautif, avec le remède qui convient au modificateur :

```
Remove the 'required' modifier from member 'Total' of type 'Order', or remove [OnDeserializing] from that
type. A pre-populate callback must observe an unpopulated instance, so members are assigned after
construction, and a 'required' member can only be set in an object initializer.
```

```
Change the 'init' accessor of member 'Total' of type 'Order' to 'set', or remove [OnDeserializing] from that
type. A pre-populate callback must observe an unpopulated instance, so members are assigned after
construction, which an init-only member does not allow.
```

Aucune des deux constructions n'est un problème en soi : ceci ne se déclenche que quand les deux sont présentes sur le même type. Sans le diagnostic, le consommateur obtiendrait à la place une erreur de compilateur à l'intérieur de source générée qu'il n'a jamais écrite.

**C'est une contrainte du chemin généré uniquement.** La *reflection path* assigne les membres par réflexion, où aucun des deux modificateurs ne s'applique, donc le même type fait un *round-trip* là sans broncher. Un type peut par conséquent sérialiser tranquillement aujourd'hui et bloquer le *build* au moment où il est enrôlé dans un *container* généré.

Des trois issues, retirer `[OnDeserializing]` est en général la bonne : c'est le seul callback des quatre avec cette contrainte, et `[OnDeserialized]` s'exécute sur l'instance entièrement peuplée sans aucune restriction. Reportez-vous-y sauf si le callback doit vraiment amorcer un état que le document entrant écrase ensuite.

### Deux changements de forme au niveau IL derrière la nouvelle hiérarchie d'attributs

`CrystalJsonConverterAttribute` et `CrystalJsonSerializableAttribute` (anciennement `CrystalJsonSerializable`) reposent désormais sous les nouvelles classes de base neutres en format :

- `CrystalJsonConverterAttribute` dérivait directement de `System.Attribute` ; il dérive maintenant de `CrystalConverterAttribute`.
- `CrystalJsonSerializableAttribute` déclarait sa propre propriété `Type[] Types { get; set; }` ; cette propriété est maintenant héritée de `CrystalSerializableAttribute`, et le type déclarant de l'attribut lui-même ne porte aucun membre `Types` propre.

**Les deux changements sont source-compatibles** : le code existant qui référence l'un ou l'autre attribut, ou lit `.Types`, recompile inchangé contre la nouvelle version, et rien dans l'usage ordinaire (construction d'attribut, accès aux propriétés, la recherche `ForAttributeWithMetadataName` propre au générateur de source, qui matche par nom de métadonnée exact quel que soit le type de base) n'est affecté. La seule population qui peut observer une différence est du code faisant sa propre réflexion sur une assembly **précompilée** buildée contre l'ancienne forme, par exemple du code qui parcourt `GetType().BaseType` en attendant `System.Attribute` directement, ou qui cherche `Types` avec `BindingFlags.DeclaredOnly` en l'attendant sur le type propre de l'attribut plutôt qu'hérité. Si vous avez un tel code (la plupart des applications n'en ont pas), recompilez-le contre le nouveau *package* plutôt que de mélanger les binaires.

### Un seul plafond de profondeur d'imbrication pour chaque format de sérialisation : `CrystalJsonWriter.MaxDepth = 64`

Les deux *writers* JSON portaient chacun leur propre plafond de profondeur privé de 16 niveaux, les chemins générés n'en avaient aucun, et le parser JSON refusait au-delà de 64. Tous les formats et le parser partagent désormais une seule constante nommée, `SnowBank.Data.Json.CrystalJsonWriter.MaxDepth = 64` (`CrystalXml.MaxDepth` est gardé comme alias pointant vers la même constante). La valeur est la profondeur maximale par défaut de System.Text.Json comme de Newtonsoft.Json, donc un document que cette bibliothèque écrit reste lisible par les *stacks* .NET grand public à leurs valeurs par défaut, et tout ce que cette bibliothèque écrit, elle peut le relire. Pour les *writers* JSON c'est **strictement un assouplissement** (64 au lieu de 16) : aucun graphe d'objets qui sérialisait avec succès avant ne peut se mettre à échouer. Les chemins générés, qui n'avaient auparavant aucun plafond, refusent maintenant au-delà de 64 avec une exception typée au lieu de faire déborder la *stack*.

### Le nommage `[CollectionDataContract]` n'a aucune existence JSON, sur aucun des deux sérialiseurs

`Name`, `ItemName`, `KeyName` et `ValueName` façonnent le fil XML uniquement. `DataContractJsonSerializer` ignore les quatre quand il écrit du JSON, donc il n'y a rien qu'une migration ait à reproduire :

```csharp
[CollectionDataContract(Name = "ItemBag",  ItemName = "entry")]                       public class ItemBag  : List<string> { }
[CollectionDataContract(Name = "LabelMap", KeyName  = "code", ValueName = "label")]   public class LabelMap : Dictionary<string, string> { }
```

```json
{ "bag": ["x","y"], "labels": [ { "Key": "c1", "Value": "Label one" } ] }
```

C'est la sortie propre du sérialiseur *legacy* : des éléments de tableau simples, et les littéraux `Key`/`Value` plutôt que `code`/`label`. Le seul sens visible en JSON de l'attribut est « ce type est une collection », que les binders de collection fournissent déjà pour les sous-classes de `List<T>`, `Collection<T>` et `Dictionary<K,V>` : un tel type est construit et rempli comme lui-même, donc `Bag` revient un `ItemBag` et `Labels` un `LabelMap`. Sous `CrystalJsonSettings.DataContractCompat` le dictionnaire prend la forme pair-array ci-dessus et binde en retour depuis elle.

Action de migration : aucune. Si un portage a planifié du travail pour reporter ces noms, supprimez cet élément de travail.

### Les dates au format Microsoft avec un suffixe d'offset préservent l'instant

Dans `"/Date(ms+HHMM)/"` les millisecondes sont toujours le décalage par rapport à l'epoch UTC ; le suffixe ne porte que l'offset local du producteur (`DataContractJsonSerializer` l'émet pour les valeurs `DateTimeKind.Local`). Le lecteur décalait auparavant la valeur de (offset local du lecteur moins offset du suffixe), ce qui produisait un instant différent sur toute machine dont l'offset différait du suffixe, et ne pouvait pas faire un *round-trip* de la propre sortie `WithMicrosoftDates()` de CrystalJson.

`JsonString.ToDateTime` fait désormais apparaître l'instant dans l'heure locale du lecteur (comme DCJS) et `ToDateTimeOffset` garde à la fois l'instant et l'offset du producteur. `TryConvertToDateTimeOffset` levait auparavant `ArgumentException` sur une telle valeur au lieu de convertir ; il convertit maintenant.

Si vous avez des attentes de test épinglées aux anciens résultats décalés, elles auront besoin d'être mises à jour. Elles dépendaient aussi de l'offset de la machine, donc elles ne tenaient que sur un seul fuseau horaire.

### Trois autres corrections de lecture de dates et de nombres

- **Une date longue localisée parse sur chaque plateforme.** Une chaîne de date commençant par une lettre n'essayait que les formes strictes `ParseExact` et échouait sans atteindre le repli indulgent `DateTime.Parse`. Les données CLDR de macOS et Linux mettent une espace fine insécable (U+202F) avant AM/PM là où Windows utilise une espace normale, donc une date formatée sur une plateforme refusait de parser sur l'autre. Elle retombe maintenant et parse.
- **Les extrêmes de `JsonDateTime` convertissent sans arithmétique d'offset.** Convertir un `DateTime.MinValue` packé en DOM vers `DateTimeOffset` levait `ArgumentOutOfRangeException` à l'est de Greenwich (et `MaxValue` à l'ouest). Les extrêmes sont des sentinelles (« pas de valeur », « la fin des temps ») et se mappent maintenant aux `DateTimeOffset.MinValue` / `MaxValue` canoniques quel que soit l'offset de la machine, donc la route DOM fait un *round-trip* d'un DTO avec une date non définie de la même façon que la route texte l'a toujours fait.
- **L'échelle décimale survit au DOM.** `JsonNumber.ToDecimal` convertissait via la valeur `double`, donc binder le littéral `1.100` donnait `1.1m` (échelle 1) au lieu de `1.100m` (échelle 3) : les chiffres d'affichage monétaire changeaient après un *round-trip* par le DOM. La conversion récupère maintenant la valeur depuis le littéral d'origine.

### `ColaRangeSet.Mark` accepte une plage dégénérée au lieu de lever une exception

`ColaRangeSet<TKey>.Mark(begin, end)` levait `InvalidOperationException` quand `begin == end`. Une plage vide ne contient rien, donc c'est maintenant un no-op : l'ensemble, son `Count` et ses `Bounds` sont inchangés. Une plage **à l'envers** (`begin > end`) lève toujours une exception, puisque c'est une véritable erreur de l'appelant.

Cela correspond à la façon dont un vrai *cluster* traite une plage de conflit vide, ce qui est là où c'est apparu : une lecture de plage dont la plage de conflit se résout comme vide (par exemple une lecture limitée inversée dont le sélecteur de fin tombe exactement sur la dernière clé retournée) crashait contre l'émulateur alors que le vrai *cluster* l'acceptait.

Si vous gardiez un appel à `Mark` contre le cas dégénéré, ou attrapiez `InvalidOperationException` autour d'un, ce code est maintenant mort.

Le message d'exception pour le cas à l'envers imprimait aussi la clé de début sous l'étiquette *End key* et la clé de fin sous *Begin key*. Si vous avez un parseur de journaux ou un test lié à ce texte, il a changé.

### La suppression de plage de `ColaOrderedDictionary` ne crashe plus quand la recherche s'épuise

`ColaOrderedDictionary.RemoveRange` et `IterateAndRemoveRange` levaient `IndexOutOfRangeException` quand la recherche de plage manquait d'entrées : sur un dictionnaire vide, sur une plage au-dessus de chaque clé, ou quand les suppressions consommaient chaque clé à ou après le début de la plage.

Une bévue de priorité d'opérateurs gardait le cas de recherche épuisée, et pour chaque itération non épuisée le mauvais *parse* calculait par hasard le prédicat voulu, ce qui explique pourquoi il est resté latent depuis l'écriture du type. Seul le code qui atteignait réellement le crash voit une différence. Si vous attrapez `IndexOutOfRangeException` autour d'une suppression de plage comme contournement, cet *catch* est maintenant mort et devrait partir.

### Encodeurs de largeur fixe de `Slice` : deux corrections au niveau du fil

Deux membres de la famille de largeur fixe produisaient de mauvais octets : `Slice.FromFixedU16BE` retournait un *slice* plus grand que les deux octets qu'il avait écrits, et les surcharges de découpe `FromFixed128BE(upper, lower)` émettaient des octets *little-endian*. Les deux produisent maintenant ce que leurs noms promettent, épinglés par des tests sur toute la famille de découpe. Les clés stockées via les surcharges cassées ne correspondent pas à la sortie corrigée.

### Le *dump* de transaction imprimait les conflits de lecture sous l'étiquette conflit d'écriture

Le second site de *dump* du débogueur de transaction lisait l'ensemble des conflits de lecture sous son en-tête « Write Conflicts », donc un *dump* imprimait le même ensemble deux fois et rapportait zéro conflit d'écriture alors que la transaction en tenait. Si un parseur de journaux ou un test était lié à ce texte, il a changé. La logique de marquage des conflits elle-même a toujours été correcte ; seul le *dump* mentait.

### Les callbacks de future natifs sont remaniés, et l'arrêt se draine de façon déterministe

Le chemin d'achèvement du client natif vers le code managé est passé à un seul callback `UnmanagedCallersOnly` avec des value-task sources poolées. Deux effets observables : moins d'allocation par opération, et un drainage déterministe des futures en attente sur `Fdb.Stop()` et le dispose de la base de données, ce qui ferme les *races* d'arrêt de longue date (issue #48). Le *build* netstandard2.0 garde le chemin par délégué marshalé.

### Aspire choisit des tags de container FoundationDB par défaut plus récents

`FdbAspireHostingExtensions` porte le dernier tag d'image docker connu par version majeure, utilisé quand vous n'en épinglez pas un.

| Constante | 7.4.2 | 7.4.3 |
|---|---|---|
| `LatestVersion74` | 7.4.6 | 7.4.6 |
| `LatestVersion73` | 7.3.70 | 7.3.76 |
| `LatestVersion72` | 7.2.9 | 7.2.8 |
| `LatestVersion71` | 7.1.62 | 7.1.66 |

Épinglez une version explicite si vous avez besoin d'une image précise. `scripts/check-fdb-image-tags.ps1` (et le jumeau `.sh`) les rafraîchit depuis Docker Hub ; il est en lecture seule sauf si vous passez `-Fix`.

### Les options d'idempotence natives sont refusées en dessous de l'api niveau 720

Poser `FdbTransactionOption.IdempotencyId` ou `AutomaticIdempotency`, via `WithIdempotencyId(...)` ou `WithAutomaticIdempotency()`, contre un *cluster* en dessous de l'api niveau 720 (fdb 7.2) lève désormais `NotSupportedException` au moment où l'option est posée. Jusqu'à la 7.4.2, le même appel produisait une erreur native obscure ou un *no-op* silencieux, donc un *handler* qui demandait l'idempotence sur un *cluster* plus ancien tournait sans elle et ne le savait jamais.

| Version | `WithAutomaticIdempotency()` contre un *cluster* en dessous de l'api niveau 720 |
|---|---|
| 7.4.2 | *no-op* silencieux ou erreur native obscure ; le *handler* continue sans idempotence |
| 7.4.3 | `NotSupportedException`, nommant l'option et la version d'api choisie |

Montez la version d'api à 720 ou plus pour utiliser l'idempotence, ou conditionnez l'appel sur `tr.Idempotency.IsSupported` (voir [Nouvelles API](#nouvelles-api)) et repliez quand elle est false. Les deux options étaient déjà présentes en 7.4.2 ; seul le refus précoce est nouveau.

### Une première ouverture de base de données ratée n'empoisonne plus le *provider*

`FdbDatabaseProvider`, l'`IFdbDatabaseProvider` enregistré en DI, verrouillait un état en échec quand sa première ouverture ratait : chaque requête suivante rendait le même échec, donc un *provider* démarré avant que son *cluster* soit joignable restait cassé pour la durée de vie du processus. Une première ouverture ratée est désormais transitoire, et une requête ultérieure réessaie et peut réussir. Rien à faire : un nœud qui démarre avant son *cluster* se rétablit tout seul.

## Nouvelles API

### CrystalJson/CrystalXml : attributs de *container* neutres en format et la table de vérité de sortie

Déclarer un *container* généré à la source est désormais scindé en trois préoccupations indépendantes : quelle classe héberge le code généré (`[CrystalConverter]`), quel(s) format(s) elle produit (`[CrystalJsonOutput]` et/ou `[CrystalXmlOutput]`), et quels types elle enrôle (`[CrystalSerializable(typeof(...))]`, neutre en format, le type enrôlé reçoit un sérialiseur généré pour chaque format que le *container* demande).

```csharp
[CrystalConverter]
[CrystalJsonOutput(CrystalJsonSerializerDefaults.Web)]
[CrystalXmlOutput]
[CrystalSerializable(typeof(User))]
[CrystalSerializable(typeof(Product))]
public static partial class ApplicationSerializers
{
    // generated code will be inserted here
}
```

`[CrystalJsonConverter]` et `[CrystalXmlConverter]` restent comme alias mono-format (marqueur + un seul format de sortie regroupés) pour le cas courant d'un *container* qui ne produit jamais qu'un seul format. Un *container* combinant un alias avec un attribut de sortie explicite, un qui ne nomme aucun format de sortie, ou un qui porte plusieurs marqueurs de *container*, est refusé au moment du *build*, voir [Diagnostics](#reference-des-diagnostics) ci-dessous.

`CrystalOutputAttribute` est la base commune (non visible dans le code généré) de `[CrystalJsonOutput]` et `[CrystalXmlOutput]`, gardée purement pour la documentation et la découvrabilité : le générateur de source matche chaque attribut de sortie par son nom de métadonnée exact, pas en parcourant cette hiérarchie, donc un type dérivé de `CrystalConverterAttribute`, `CrystalOutputAttribute`, ou `CrystalSerializableAttribute` lui est invisible et ne s'enrôle pas comme format ou marqueur de *container* reconnu. Ne sous-classez aucun des trois.

La table de vérité complète, le pipeline d'exécution, les profils compat (`DataContract`) et XML moderne, et chaque diagnostic en détail sont documentés dans [`Documentation/CrystalXml.md`](../CrystalXml.md) ; cette entrée ne résume que ce qui a changé par rapport à 7.4.2.

#### Référence des diagnostics

Une ligne chacun, pour les diagnostics introduits ou remodelés par cette version :

| Diagnostic | Sévérité | Signification |
|---|---|---|
| `CRYS0001` | Error | `[CrystalConverter]` ne nomme aucun format de sortie ; le *container* ne générerait rien |
| `CRYS0002` | Error | Un alias mono-format (`[CrystalJsonConverter]`/`[CrystalXmlConverter]`) est combiné avec un attribut de sortie, que l'alias ne peut pas exprimer |
| `CRYS0003` | Error | Un *container* porte plusieurs marqueurs de *container*, ce qui fait deux réponses à « que produit ce *container* » |
| `CJSON0010` | Error | `[JsonConvertWith]` nomme un type qui n'implémente ni `IJsonPacker<T>` ni `IJsonDeserializer<T>` pour le type du membre |
| `CJSON0011` | Error | Un membre déclare deux noms de fil différents pour deux sérialiseurs (`[DataMember(Name = ...)]` à côté d'un renommage étranger en désaccord) |
| `CJSON0019` | Warning | Un enrôlement `[CrystalSerializable]` nomme un type que CrystalJson sérialise déjà nativement ; aucun convertisseur n'est généré pour lui |
| `CJSON0020` | Info | La surface de proxy JSON générée (`ToReadOnly`/`ToMutable`, les types de proxy) est sautée parce que la compilation est en dessous de .NET 7+/C# 11 ; le convertisseur, le `TypeMapper`, et toute sortie XML demandée ne sont pas affectés |
| `CJSON0021` | Error | Un `[CrystalSerializable]` enrôle un type que le compilateur ne peut pas résoudre ; corrigez l'erreur de compilation sur le type enrôlé |
| `CXML0001` – `CXML0013` | surtout Error, `CXML0012` Info | Les règles spécifiques au XML (format DataContract vs politique de nommage, *container* de sérialiseur manquant, projections d'attribut invalides, collisions de noms, noms d'*inner-item* manquants, noms XML invalides, convertisseurs sans facette XML, `[CollectionDataContract]` non respecté sur le format DataContract, formes de dictionnaire sans forme lexicale, settings inertes, et la propriété `[DataMember]` get-only que le format compat refuse), voir `Documentation/CrystalXml.md` pour la table complète |

### CrystalJson : le preset `DataContractCompat`, et l'émission de durée *legacy*

`CrystalJsonSettings.DataContractCompat` est un preset nommé et mis en cache qui reproduit le fil `DataContractJsonSerializer` **complet** : enums numériques, dates `\/Date(ms)\/`, chaînes de durée ISO 8601 pour `TimeSpan`, dictionnaires `[{"Key":..,"Value":..}]`, et membres `null` explicites. Un endpoint qui doit alimenter un lecteur *legacy* inchangé devient une seule référence de settings au lieu d'une composition en cinq appels (qui reste octet-équivalente : le preset et la chaîne fluent sont la même instance mise en cache). Cadrez-le par endpoint : l'émission des null explicites en particulier est de la pure verbosité pour tout consommateur qui n'est pas un lecteur *legacy* figé.

La moitié durée est nouvelle aussi : `WithIso8601Durations()` sérialise `TimeSpan` sous la forme *legacy* `"P1DT2H3M4.005S"` au lieu du nombre de secondes par défaut (`WithNumericDurations()` restaure le défaut), sur les routes texte et DOM. La lecture accepte les deux formes quels que soient les settings.

Un *container* généré à la source peut cuire le preset comme son fil par défaut : `[CrystalJsonConverter(CrystalJsonSerializerDefaults.DataContractCompat)]` fait que les points d'entrée générés du *container* émettent le fil *legacy* quand l'appelant ne passe aucun settings, alors que des settings passés explicitement remplacent toujours le profil entièrement. Le profil gouverne uniquement les formats de valeur et est indépendant de l'appartenance : il sert les DTO simples sous les règles d'opt-out POCO de DCJS, et les types `[DataContract]` sous le modèle DataContract (voir le changement cassant ci-dessus), de la même façon qu'un *container* sans profil. Pour les types qu'il sert, un tel *container* produit ce que DCJS aurait produit, avec les différences documentées (ordre des membres, pas d'échappement `\/` en dehors des littéraux de date, `-0.0` en `0`, et refus bruyants là où DCJS résolvait silencieusement les conflits à deux sérialiseurs). Combiner le profil avec une politique de nommage (camelCase et consorts) est refusé au moment du *build* (**`CJSON0013`**) ; `PropertyNameCaseInsensitive` n'est pas refusé, puisqu'il gouverne seulement comment un nom de membre entrant est matché à la lecture et ne change rien de ce que le profil écrit. La forme voulue pour un portage progressif est le *container* double : les services *legacy* sur le *container* compat, les modernisés sur un *container* par défaut ou `Web` sur les mêmes types ; supprimez le *container* *legacy* quand le portage est terminé.

### CrystalJson : émission de dictionnaire *legacy*

`CrystalJsonSettings.WithDictionariesAsPairArrays()` sérialise chaque dictionnaire comme `[ {"Key":..,"Value":..}, ... ]` au lieu d'un object map JSON, pour les clients *legacy* qui ne savent pas lire les maps. C'est désactivé par défaut, et la forme est toujours acceptée à la lecture quoi qu'il arrive. `WithDictionariesAsMaps()` restaure le défaut.

Les clés sont émises avec leur type JSON naturel (clés chaîne comme chaînes, clés numériques comme nombres), correspondant à DCJS. Le commutateur est respecté par la *reflection path* et les *generated converters*, puisque les deux passent par le *text writer*. La route DOM garde le modèle object-map, parce qu'un `JsonObject` *est* une map : sérialisez à travers le *text writer* pour produire la forme *legacy*.

### CrystalJson : `[JsonConvertWith]`, l'attribut de convertisseur natif

`[JsonConvertWith(typeof(X))]` attache un convertisseur CrystalJson à un membre ou à un type, où `X` implémente la paire `IJsonPacker<T>` / `IJsonDeserializer<T>`. Les deux chemins le reconnaissent, alimentant le même slot que les orthographes étrangères. La reconnaissance est **par facette** : un type qui n'implémente qu'une moitié sert cette direction, et le traitement par défaut couvre l'autre, ce qui est la recette de la sérialisation asymétrique.

La doctrine : gardez le `[JsonConverter(typeof(...))]` de System.Text.Json seulement quand le convertisseur nommé est valide pour System.Text.Json aussi, pour que les deux sérialiseurs fassent la même chose. Un convertisseur CrystalJson-seulement derrière l'attribut STJ empoisonne le type pour STJ (un `InvalidOperationException` à l'exécution, ou une erreur de *build* source-gen STJ) ; un tel convertisseur porte l'attribut natif, que STJ n'inspecte jamais.

Priorité quand plusieurs s'appliquent : l'attribut natif l'emporte sur `[JsonBooleanLiterals]` et sur les deux orthographes étrangères `[JsonConverter]`. Et contrairement aux orthographes étrangères, un `[JsonConvertWith]` nommant un type sans la paire Pack/Unpack échoue bruyamment : une exception de construction de métadonnée sur la *reflection path*, l'erreur de *build* **`CJSON0010`** via le générateur. C'est notre propre attribut ; le silence ne ferait que cacher une faute de frappe.

### CrystalJson : convertisseurs de membre pour la forme nullable

Un convertisseur de membre peut désormais être déclaré pour la forme nullable elle-même : `IJsonMemberConverter<DateTime?>` (ou une seule facette de celui-ci) sur un membre `DateTime?`. Le pont sonde d'abord le type **exact** du membre, puis retombe sur le *lift* existant, sur la *reflection path* comme sur le générateur, donc chaque convertisseur `T` continue de fonctionner inchangé, et rien ne pouvait dépendre de la forme `T?` avant, puisqu'elle était refusée sur le chemin natif et ignorée sur l'étranger.

L'intérêt de la forme `T?` est l'entrée **présente-mais-illisible** : les convertisseurs *legacy* (les protocoles de l'ère DCJS en particulier) traitent souvent une chaîne vide ou impossible à parser comme « pas de valeur », et un convertisseur déclaré pour `T` ne peut jamais répondre ça, parce qu'il doit retourner un `T`. Déclaré pour `T?`, le convertisseur possède chaque valeur *présente* et peut répondre `null`, distinctement de `default(T)`, qui reste une valeur de domaine légitime (`0` pour un `int?`, l'an 1 pour un `DateTime?`), et de JSON null ou d'un membre manquant, que le pipeline gère toujours avant le convertisseur des **deux** côtés. Cette dernière partie signifie que la déclaration `T?` ne transfère que le côté lecture : `Pack` ne voit jamais null, et le fil de membre null continue de suivre les settings (`WithNullMembers()` etc.), donc un convertisseur *legacy* dont la forme d'*écriture* de membre null n'est pas JSON null (par exemple une chaîne vide) reste non portable côté écriture par conception. Un convertisseur `T?` nommé sur un membre NON nullable reste un refus bruyant sur les deux chemins.

### CrystalJson : types auto-sérialisables

`[CrystalJsonSelfSerializable]` est un **méta-attribut** : vous l'appliquez à l'une de *vos propres* classes d'attribut, et chaque type décoré avec cet attribut est opté dans la génération de source JSON. Un layer peut opter ses propres types dedans sans coupler l'application consommatrice au générateur.

```csharp
// the layer declares its marker attribute once
[CrystalJsonSelfSerializable]
public sealed class MyEntityAttribute : Attribute { }

// the application just declares an entity
[MyEntity]
public sealed partial record Widget { public required string Name { get; init; } }
```

Un type marqué agit comme son propre *container*. Tout ce qui est généré atterrit dans **une** classe statique imbriquée nommée `Json`, donc l'entité réserve exactement un nom de membre :

```csharp
Widget.Json.Default          // the converter
Widget.Json.ReadOnly         // read-only proxy
Widget.Json.Writable         // writable proxy
Widget.Json.PropertyNames    // property-name constants
Widget.Json.GetResolver()    // the per-container resolver
```

Les types référencés par l'entité sont toujours parcourus et s'imbriquent dans cette même portée sous leurs noms simples, où ils ne peuvent pas masquer le type référencé dans la source propre de l'entité. Le nom unique réservé est délibéré : un futur générateur pour un autre format réclame une portée sœur (`Widget.Cbor`) sans renégocier quoi que ce soit. Cela signifie aussi que toute la portée `Json` est du code généré, donc elle porte les attributs de code généré qui ne pouvaient pas être placés sur la partielle de l'entité, qui est votre source. Les noms d'indice en self-mode sont qualifiés par namespace, puisque les noms d'entité entrent en collision bien plus souvent que les noms de *container*.

Contraintes et leurs diagnostics :

| Diagnostic | Sévérité | Cause |
|---|---|---|
| `CJSON0004` / `CJSON0005` | error | l'entité n'est pas `partial`, ou est générique, ou est imbriquée |
| `CJSON0006` | error | l'entité déclare déjà un membre nommé `Json`. Renommez-le et gardez le nom de fil avec `[JsonProperty("json")]`, ou utilisez un *container* `[CrystalJsonConverter]` à la place |
| `CJSON0007` | warning | un type référencé porte un nom comme un membre de portée ; il est exclu de la génération et retombe sur la sérialisation à l'exécution |

Le chemin de *container* `[CrystalJsonConverter]` existant est intact.

### Expérimental : `FdbTextIndex`

`FoundationDB.Layers.Experimental` a gagné un layer de recherche plein texte avec des requêtes de terme, de phrase et de proximité et un scoreur à somme pondérée (style BM25).

**Ce layer est expérimental** : il vit sous `Layers.Experimental` précisément parce que la disposition de son *keyspace* et son API sont encore libres de bouger entre versions mineures. Ne mettez pas encore un index de production dessus.

### `FdbErrorDebugger` : la traduction d'erreurs du client, exposée pour les oracles de test

`FoundationDB.Client` a gagné un petit proxy statique sur les internes de traduction d'erreurs du client natif, pour que le code de test puisse les observer sans octroi `InternalsVisibleTo`. C'est le pendant côté erreur du `FdbTransactionDebugger` existant.

```csharp
FdbErrorDebugger.GetErrorMessage(code);                                  // fdb_get_error
FdbErrorDebugger.MapToException(code);                                   // the exception the client would throw
FdbErrorDebugger.TestErrorPredicate(FdbErrorPredicate.Retryable, code);  // fdb_error_predicate
```

Son usage prévu est comme **oracle** : les suites de conformité épinglent les réponses du client natif et tiennent le comportement de l'émulateur contre elles.

**Cela ne change pas comment vous gérez les erreurs, et vous ne devriez pas l'utiliser pour ça.** La gestion des erreurs appartient à la *retry loop* (`db.ReadAsync` / `WriteAsync` / `ReadWriteAsync`), qui applique déjà ces prédicats pour vous. Lire `TestErrorPredicate(Retryable, ...)` dans le code applicatif pour décider s'il faut réessayer réimplémente la boucle à la main, mal, et c'est exactement l'erreur que la *retry loop* existe pour empêcher. Rien dans votre gestion d'erreurs existante n'a besoin de changer parce que ce type existe maintenant.

Chaque membre appelle dans `fdb_c`, donc aucune connexion à un *cluster* n'est nécessaire, mais la bibliothèque native doit être déployée ou l'appel lève `DllNotFoundException`.

### CrystalJson : `[JsonProperty(NumberFormat = String)]`, les nombres en chaînes

Un membre numérique peut opter pour la forme chaîne, le même bouton par membre qu'`EnumFormat` :

```csharp
[JsonProperty(NumberFormat = JsonNumberFormat.String)]
public long AccountId { get; init; }
// => {"AccountId": "12345678901234567"} instead of {"AccountId": 12345678901234567}
```

La chaîne est exactement le littéral que la forme numérique aurait produit (échelle décimale incluse), ce qui protège les valeurs 64 bits de la perte de précision des consommateurs JavaScript. La lecture accepte toujours les deux formes, avec ou sans l'attribut, donc producteurs et consommateurs bougent indépendamment. Respecté par la *reflection path*, les *generated converters*, la route DOM, et les setters de proxy writable, avec un test de parité d'octets à travers les chemins. Aucun défaut ne change : les membres sans l'attribut gardent la forme numérique.

### Les messages de `FdbException` viennent d'une table managée

`FdbErrorMessages.TryGetMessage(FdbError)` est une table de 337 entrées générée à partir des propres réponses `fdb_get_error` du client déployé, épinglée octet-égale par un test. `FdbException(FdbError)` se résout à travers elle, donc le constructeur code-seul fonctionne sur un processus sans `fdb_c` (FakeDb et autres backends managés), et un code connu ne coûte aucun appel interop. `fdb_get_error` reste le repli pour un code plus récent que ce *build*.

### FakeDb : un *store* de données validées enfichable, et une conformité plus proche

Les données validées de l'émulateur en mémoire ont bougé derrière un point d'extension public dans le nouveau namespace `FoundationDB.Storage` : `IFdbCommittedStore` et `IFdbCommittedCursor`, avec `ColaCommittedStore` comme backend intégré. Un backend hors assembly peut désormais enficher son propre stockage.

La version porte aussi une campagne de conformité qui tient l'émulateur contre un vrai *cluster* : la résolution de sélecteurs autour des opérations atomiques en attente, la rétention de conflit de lecture de `CompareAndClear`, et l'ancrage des clés de frontière pour `GetKey` et `GetRange` correspondent maintenant au vrai client là où ils divergeaient. Un test épinglé à l'ancienne réponse fausse de l'émulateur voit la corrigée.

### FdbTop et FdbShell

`FdbTop` parse désormais les arguments de ligne de commande au lieu de seulement lire les défauts. Les deux outils ont gagné un `README.md`, et `FdbShell` ne produit plus de token de commande vide quand ENTRÉE achève une commande qui ne prend pas d'arguments.

### `tr.Idempotency` : une sonde de capacité pour l'idempotence native

`FdbIdempotencyFacet`, atteint via l'extension `tr.Idempotency` sur une transaction, expose un seul membre, `IsSupported` : true quand le *cluster* connecté tourne en api niveau 720 ou plus (fdb 7.2+), là où l'idempotence native est disponible.

```csharp
if (tr.Idempotency.IsSupported)
{
    tr.Options.WithAutomaticIdempotency();
}
// sinon, continuer sans, ou appliquer votre propre repli
```

Un *handler* l'utilise pour décider s'il faut activer `WithAutomaticIdempotency()` ou `WithIdempotencyId(...)`, au lieu de poser l'option à l'aveugle et d'attraper la `NotSupportedException` qu'un *cluster* plus ancien lève maintenant (voir [Changements de comportement](#changements-de-comportement)). `FdbIdempotencyFacet.MinimumApiVersion` est la constante `720`.

### `Fdb.Provisioning.EnsureDatabaseConfiguredAsync` : provisionner un *cluster* neuf

Un *cluster* FoundationDB sur un volume de stockage tout neuf n'a pas de base de données tant que `configure new` n'a pas tourné une fois ; jusque-là chaque transaction attend indéfiniment et `status` rapporte la base de données comme indisponible. `Fdb.Provisioning.EnsureDatabaseConfiguredAsync` exécute cette étape, attend que la base de données réponde, et est sûr face à des démarreurs concurrents (le refus de `configure new` sur une base de données déjà configurée compte comme un succès). L'API cliente ne peut pas écrire la configuration, donc l'appelant fournit un moyen de lancer `fdbcli` dans le serveur, par exemple un `docker exec` dans le *container*.

Les *clusters* hébergés par Aspire et le *test harness* Testcontainers l'appellent désormais au premier démarrage, donc un *cluster* de développement local neuf se provisionne tout seul sans étape manuelle `fdbcli --exec "configure new single ssd"`. Ne l'appelez directement que quand vous provisionnez un *cluster* vous-même.

### `CrystalJsonSettings.Canonical()` : sortie déterministe pour le hachage

`CrystalJsonSettings.Canonical()` (relu comme `IsCanonicalOutput`, effacé par `NotCanonical()`) écrit une forme canonique déterministe, donc deux sérialisations de valeurs égales produisent une sortie octet-identique. C'est pour les comparaisons *golden-file*, le hachage, et le stockage adressé par contenu, et c'est désactivé par défaut.

### Ajouts plus petits

- `BitMap64.FindSpan(span, start)` : l'index de la première suite de N bits contigus à 1.
- `SimpleTest.ShouldNotHappenWithin(condition, duration, message)` : affirme qu'une condition reste fausse pendant toute la durée, en formes sync et async ; le pendant négatif des helpers de stabilisation existants.
- Le décodeur de capture de paquets (`SnowBank.Networking.PacketCapture`) décode de façon indulgente et ne lève plus d'exception sur un *dump* malformé.

## *Build* et outillage

Pertinent seulement si vous buildez le SDK depuis les sources, le consommez comme submodule, ou lancez ses suites de tests.

- **.NET 11 preview 7.** L'épingle du SDK dans `global.json` est `11.0.100-preview.7.26381.103`, et la vague de *packages* Microsoft est passée à `11.0.0-preview.7.26381.103` (leg net11) et `10.0.11` (legs net10 et net8). Les bibliothèques multi-ciblent toujours `net8.0`, `net10.0` et `net11.0` : **le plancher .NET 8 n'a pas bougé.**
- **`dotnet test` a désormais besoin d'un opt-in dans `global.json`.** Chaque projet de test utilise le runner NUnit Microsoft.Testing.Platform (MTP), et VSTest a disparu du workflow. Sur le SDK .NET 10+, MTP v2 refuse de tourner sous l'ancien pont VSTest et échoue avec *"Testing with VSTest target is no longer supported by Microsoft.Testing.Platform"*. Si vous buildez ce dépôt depuis les sources, ou si vous lancez vos propres suites MTP, ajoutez le runner de test à votre `global.json` :
  ```json
  {
    "test": { "runner": "Microsoft.Testing.Platform" }
  }
  ```
  La propriété MSBuild `TestingPlatformDotnetTestSupport` était le pont pour l'ancien chemin et n'a plus aucun effet sur .NET 10+. **Cadrez le lancement sur une cible moderne** (`-f net10.0`) : le mode MTP exige que chaque projet du lancement utilise le runner MTP, donc une solution qui a encore des legs `net472` (ce dépôt en a quatre) est rejetée avec *"All projects must use that test runner"* sauf si le TFM est cadré. Les legs net472 gardent le runner console NUnit, inchangé. Lancer l'assembly de test directement fonctionne dans les deux cas, et saute le *build* :
  ```bash
  dotnet artifacts/bin/<Project>/debug_net11.0/<Project>.dll --filter "FullyQualifiedName~<NamePart>"
  ```
- **Le plancher de langage du générateur de source JSON est C# 9, vérifié explicitement.** Le premier acte du générateur est une porte de version de langage qui signale **`SYSLIB1221`** (« language version not supported by the source generator ») et s'arrête quand la compilation est en dessous de C# 9. `<LangVersion>latest</LangVersion>` la passe avec de la marge, mais l'exigence réelle est seulement `>= 9` ; le déclencheur classique est un projet porté qui épingle encore un `<LangVersion>7.3</LangVersion>` de l'ère netfx.
- **Le code JSON généré ne s'appuie plus sur les *global usings* du projet.** Les fichiers générés n'émettent aucune directive `using` et qualifient désormais entièrement chaque nom BCL, et ils sont sans avertissement sous leur propre `#nullable enable` même pour des membres déclarés dans un projet inattentif au nullable. Les projets qui activaient `ImplicitUsings` (ou ajoutaient des *global usings* manuels) seulement pour arrêter les murs de `CS0246` dans les fichiers générés peuvent laisser tomber ce contournement, et les *builds* warnings-as-errors ne trébuchent plus sur `CS8600`/`CS8603`/`CS8625` dans le code généré.
- **`CS1591` (commentaire de doc XML manquant) est muté sur les *builds* Release.** Les *builds* Debug ne sont pas affectés, donc les avertissements sont toujours là pendant que vous travaillez.
- **Nouveau diagnostic `CJSON0012`** (avertissement, supprimable) : un membre `internal` sans signal d'inclusion/exclusion est sérialisé par les *generated converters* mais invisible à la *reflection path*. L'inclusion est gardée pour la compatibilité de fil ; l'avertissement rend la divergence observable pour que l'intention soit épinglée avec `[JsonInclude]` ou `[JsonIgnore]`. (`SYSLIB1038` ne se déclenche plus : les membres `[JsonInclude]` non publics sont maintenant générés via des *accessor thunks* au lieu d'être omis.)
- **Nouveaux diagnostics `CJSON0004` / `CJSON0005`**, signalés sur un type auto-sérialisable qui n'est pas `partial`, est générique, ou est imbriqué.
- **Nouveaux scripts** : `scripts/build.ps1` / `scripts/pack.ps1` (et jumeaux `.sh`) pour des *builds* autonomes, et `scripts/check-fdb-image-tags.ps1` / `.sh` pour rafraîchir les constantes de tag docker Aspire depuis Docker Hub.
- **`DownloadBinaries.sh`** rejoint `DownloadBinaries.ps1` dans `FoundationDB.Client.Native/` pour récupérer les binaires natifs `fdb_c` sur macOS et Linux (nécessite `curl` et `python3`).
- **Les lectures de `SliceReader` sont GC-safe sur le *build* netstandard2.0.** Le shim de span lite distribuait des pointeurs que le GC ne suit pas, donc un compactage entre la capture et la lecture pouvait décoder des octets périmés ; observé comme des échecs net472 non déterministes sous pression mémoire. Le chemin lite passe maintenant par des références suivies.
- **Le code généré ne casse plus sur un `T?` value type ou un membre en lecture seule.** Une substitution de style `GenericBox<int>` émettait `Nullable<int>` là où `int` était déclaré, et un membre get-only recevait une assignation d'initialiseur d'objet (`CS0200`). Un membre en lecture seule est maintenant sérialisation-seulement : écrit sur le fil, sauté à la lecture.
- **`CORESDK_STANDALONE_BUILD`** est défini quand le dépôt est buildé en autonome plutôt que comme submodule.
- **Les legs net472** forcent désormais `PlatformTarget=x64` et suppriment les avertissements de *build* de support de TFM.
- `SnowBank.SourceAnalysis` a été extrait comme bibliothèque helper Roslyn partagée, consommée **par source**, pas comme *package* : cela ne change rien pour les consommateurs.
- **La suite de certification XML tourne désormais sur la cible de validation net472 aussi**, aux côtés de la vérification de *build* netstandard2.0 existante : le chemin lite est exercé sur le vrai CLR .NET Framework pour la sortie XML exactement comme il l'était déjà pour JSON.
- **Le code généré pour un *container* XML-seulement compile sur le consommateur lite (netstandard2.0/net472).** Aucune fonctionnalité de langage ou de runtime spécifique à l'émission XML n'exige plus que le plancher existant du générateur.

## Rien à faire

Consigné pour que vous puissiez distinguer « pas d'entrée » de « pas regardé » :

- Les API publiques de transaction, clé, subspace et directory de `FoundationDB.Client` sont inchangées en 7.4.3.
- `CrystalJsonSettings.AllowTrailingData()` et `WithoutComments()` sont parfois supposés nouveaux ici. Ils ont été livrés en **7.4.2**.
- `FdbMutationType.ByteMin` / `ByteMax` sont antérieurs à 7.4.2 aussi.
- Les *containers* JSON-seulement existants (`[CrystalJsonConverter]`, ou `[CrystalConverter]` + `[CrystalJsonOutput]`) génèrent exactement ce qu'ils généraient en 7.4.2 ; rien du format JSON lui-même n'a bougé.
