# Migrating from 7.4.2 to 7.4.3

What changed for you between the `7.4.2` packages and `7.4.3`, and what you have to do about it.

Most applications upgrade by bumping the package version and rebuilding. The two sections you must read are
[Breaking changes](#breaking-changes) and [Behavior changes](#behavior-changes); the rest is informational.

## How to read this

| Section | What it means for you |
|---|---|
| [Breaking changes](#breaking-changes) | your code no longer compiles, or a required signature moved |
| [Behavior changes](#behavior-changes) | your code still compiles, but does something different at run time (often on the wire) |
| [New APIs](#new-apis) | nothing to do, unless you want the feature |
| [Build and tooling](#build-and-tooling) | only if you build from source, or you run the test suites |

## Breaking changes

### `TokenMap` and `TokenDictionary` are now compile errors on net9+

`TokenMap<T>`, `ByteStringTokenMap`, `CharStringTokenMap` and the `TokenDictionary` backing type were already
marked `[Obsolete]` on net9+ in earlier releases. The six attributes are now `[Obsolete(error: true)]`, so any
remaining use fails the build.

```csharp
// BEFORE (warning on net9+)
var map = new CharStringTokenMap();

// AFTER: use the BCL alternate lookup
var lookup = dictionary.GetAlternateLookup<ReadOnlySpan<char>>();
```

The types remain usable on `net8.0`, `netstandard2.0` and `net472`, which have no `AlternateLookup`
equivalent. Removal is a next-major move, not a 7.4.x one.

### Generated converters now honor `[JsonIgnore]`

This is a **wire change** for anyone who uses `[CrystalJsonConverter]` source generation on a type that carries
a `[JsonIgnore]`, the `System.Text.Json` spelling or the Newtonsoft (JSON.NET) one. Until 7.4.2 the generator
recognized neither and serialized the member anyway, while the reflection path had always excluded it (matching
`[JsonIgnore]` by name, any namespace) on a type **without** `[DataContract]` (on a `[DataContract]` type the
reflection path has its own change, next section). The two paths now agree, for both spellings.

```csharp
[JsonIgnore] public string Secret { get; set; }                  // 7.4.2 generated converter: emitted. 7.4.3: absent.
[Newtonsoft.Json.JsonIgnore] public string Legacy { get; set; }  // same, the JSON.NET spelling is honoured in 7.4.3
```

If a consumer of your generated converter depended on that member being present, either drop the attribute or
give it an explicit condition (below).

Members are also removed from the generated proxies, not just from serialization, so
`MyJson.Widget.ReadOnly.Secret` disappears from the generated surface as well.

### An unconditional `[JsonIgnore]` next to an include signal is now refused, loudly

A member carrying an **unconditional** `[JsonIgnore]` (no `Condition`, or `Condition = Always`, or the JSON.NET
spelling) next to an **include signal** (`[DataMember]`, `[JsonInclude]`, or a `[JsonProperty]`-style naming
attribute) is refused on both paths: the reflection path **throws when the type's contract is built** (once,
cached, both directions), and the source generator reports **error `CJSON0008`** at the member's location. This
is a deliberate behavior change: the combination used to resolve **silently**, and how it resolved changed
between versions, which is exactly the kind of silent wire movement this release refuses everywhere else:

| Version | Member with `[DataMember]` + unconditional `[JsonIgnore]`, reflection path |
|---|---|
| 7.4.2 | **included** (the `[DataMember]` opt-in gate ran before the `[JsonIgnore]` check) |
| 7.4.3-rc.1 | **excluded, both directions**, with no diagnostic |
| 7.4.3 | **refused loudly** (contract-build throw; the generator errors) |

The population that writes both attributes is the **dual-output DTO**: one serializer's wire carried the member
(`[DataMember]`, or a `[JsonProperty]` rename), the other's did not (`[JsonIgnore]`). A dual-output DTO is not
supported, and will not be: **the remedy is the split, one DTO per serializer, each with a single coherent set
of attributes** (the same steering as the "two different wire names" refusal, which is the same defect through
the naming attributes). If the pair is simply a slip on a normal single-output DTO, remove one of the two
attributes; which one depends on which intent was real. Do **not** "fix" the error by giving the `[JsonIgnore]`
a `Condition`: a `Condition` turns the member into an *included* member with a write rule, so the build error
disappears while the member ships onto the second wire for the first time.

A conditional `[JsonIgnore(Condition = ...)]` stays legal everywhere, including next to `[DataMember]`: it is
the `EmitDefaultValue=false` recipe, and it never changes membership.

**Sizing note for upgrades**: the refusal covers the Newtonsoft-style pair (`[JsonProperty]` + `[JsonIgnore]`)
as well, so a Newtonsoft-heavy codebase should measure that population *before* upgrading: every such member
becomes a build or contract-build error, not a silent drop.

### A member that declares two different wire names for two serializers is refused

A member carrying more than one naming attribute with a **different** name is one type trying to serve two
wire contracts at once: whichever name a serializer picks, one of the two consumers receives the wrong
document. This covers `[DataMember(Name = "x")]` against a JSON naming attribute, and the three JSON naming
attributes against each other: CrystalJson `[JsonProperty("x")]`, System.Text.Json `[JsonPropertyName("y")]`,
and Newtonsoft `[JsonProperty("z")]`. The reflection path throws at contract build, naming the member, both
attributes and both names; the source generator reports **error `CJSON0011`** at the member. Both directions
refuse, since read and write share the contract.

```csharp
[DataMember(Name = "id"), JsonProperty("identifier")]        // 7.4.2: one name silently won. 7.4.3: refused.
public string? Id { get; set; }

[JsonProperty("A"), Newtonsoft.Json.JsonProperty("B")]       // also refused: two JSON names on one member
public string? Code { get; set; }
```

A **lone** Newtonsoft `[JsonProperty]` name is now honoured on both paths: the generated converter learned it
in 7.4.3, and the reflection path already used it, so both routes produce the same wire (7.4.2 generated the
raw member name, ignoring the attribute). When several naming attributes are present and agree, the effective
name comes from the highest-priority one, CrystalJson `[JsonProperty]` then `[JsonPropertyName]` then Newtonsoft
`[JsonProperty]`; a disagreement among them is the refusal above. The remedy for a real conflict is the same
split as for the `[JsonIgnore]` refusal: one DTO per serializer, each with a single coherent set of attributes.

### A `[DataContract]` type enrolled in a generated container now gets the DataContract wire

Until this release the generator accepted such a type and silently ignored its DataContract attributes: all
public members, C# names. That produced a **different wire than the reflection path**, which honors the
`[DataMember]` opt-in, renames, `IsRequired`, and non-public members. Two wires for the same type, selected by
which path happened to serialize it, is exactly the silent divergence this release refuses everywhere else.

Generated converters now implement the DataContract membership model, so both paths agree:

```csharp
[DataContract]
public sealed class Order
{
    [DataMember(Name = "id")]          public string? Id { get; set; }
    [DataMember(Name = "total")]       private decimal Total { get; set; }   // non-public: included
    public string? Scratch { get; set; }                                     // no [DataMember]: excluded
}
```

```json
// 7.4.2 generated: {"Id":null,"Scratch":null}      <- DataContract attributes ignored
// 7.4.3 generated: {"id":null,"total":0}           <- same as the reflection path
```

What the generated path applies: `[DataMember]` as the sole membership opt-in (a public member without it is
**excluded**), `Name=` renames, non-public members and accessors (reached through accessor thunks), and
`IsRequired = true` (an absent member throws on read; an explicit `null` satisfies it, as `DataContractJsonSerializer`
does). `Order=` and `EmitDefaultValue=` are not read, on either path.

**Member order is declaration order, and it does not match DCJS.** `DataContractJsonSerializer` emits the
members that carry no `Order=` first, alphabetically by their wire name, then the ones carrying
`[DataMember(Order = n)]` in ascending `n`. This library emits declaration order, on the reflection path and in
generated converters alike. The difference is invisible to any conforming JSON reader, since object members are
unordered by definition, and it is visible to anything that compares the bytes: a golden-file diff against a
captured legacy response, a hash or checksum over the payload, or content-addressed deduplication. If you need
the bytes to match, reorder the declarations; there is no setting that restores the DCJS order.

**This is a wire change for any type that was already enrolled**, in the direction of the reflection path. If
you relied on the old all-public/C#-names output, that wire is still reachable on purpose: remove the
DataContract attributes from the type, or split off a plain DTO, either of which makes the intent explicit
rather than an accident of the path.

A `[DataContract]` type merely *referenced* by an enrolled DTO's member was always fine and still is: inside
generated code it routes through the runtime resolver, which applies the same model.

### `[CrystalJsonSerializable]` is obsolete, use `[CrystalSerializable]`

Enrolling a type in a source-generated container is now format-neutral: the same attribute serves every
output format the container requests (JSON, XML, or both), rather than one attribute per format. `[CrystalSerializable(typeof(...))]`
is the new spelling; `[CrystalJsonSerializableAttribute]` still compiles but is marked `[Obsolete]` (a `CS0618`
warning, not an error - nothing fails the build yet):

```csharp
// BEFORE (still compiles, now a CS0618 warning)
[CrystalJsonSerializable(typeof(Widget))]

// AFTER
[CrystalSerializable(typeof(Widget))]
```

The rename is mechanical: search for `CrystalJsonSerializable` and replace with `CrystalSerializable`. See
[New APIs](#new-apis) below for the full attribute model this belongs to, and
[`Documentation/CrystalXml.md`](../CrystalXml.md) for the complete truth table.

### `IJsonPacker<T>.Pack` takes a `ref CrystalJsonPackContext`

The interface's only member changed from `Pack(T instance, CrystalJsonSettings? settings = null,
ICrystalJsonTypeResolver? resolver = null)` to `Pack(ref CrystalJsonPackContext context, T instance)`. The
context carries the settings, the resolver, the nesting depth, and the visited-object stack of the whole
packing walk, by ref through every nested call, including the collection/dictionary pack helpers. Before,
those helpers could only call the three-argument member, so the recursion guards reset at each collection
boundary and a reference cycle running through a `List<T>` member crashed the process on a
`StackOverflowException`; now it raises the same catchable recursion error as every other path.

Who is affected, and what to do:

- **Code that calls `Pack(instance, settings, resolver)`** keeps compiling and behaving the same: that shape
  survives as an extension method that opens a fresh context and forwards.
- **Source-generated containers** pick up the new shape by recompiling; nothing to edit.
- **Hand-written `IJsonPacker<T>` implementations** (custom converters named in `[JsonConvertWith(...)]`) must
  change their signature to `Pack(ref CrystalJsonPackContext context, T instance)`; read the settings and
  resolver from the context. A converter that packs nested values passes the same context along.
- Precompiled assemblies built against the old interface must be recompiled; do not mix binaries across this
  change.

### `CrystalJsonSettings.OptionFlags.EnumsAsString` is now a compile error

The flag bit is renamed `EnumsAsNumbers`, with the opposite meaning, because the default wire form for enums
flipped to strings (see [Behavior changes](#behavior-changes)). The old member survives as
`[Obsolete(error: true)]`, so the build failure names the replacement. The `EnumsAsString` boolean property and
the `WithEnumAsStrings()` / `WithEnumAsNumbers()` fluent methods keep their names and semantics. Only code that
manipulates `OptionFlags` directly is affected.

### `IFdbDatabase.BeginTransactionAsync` is now a compile error

The three-argument `BeginTransactionAsync(FdbTransactionMode, CancellationToken, FdbOperationContext?)` carried
`[Obsolete]` as a warning in 7.4.2 and now carries `[Obsolete(..., error: true)]`. The member is still there, so
the build fails with a message naming the replacement rather than with a missing member.

Call `BeginTransaction(...)` instead. The overload has been `[EditorBrowsable(Never)]` for a while, so a
surviving callsite predates that.

## Behavior changes

### `[JsonIgnore(Condition = ...)]` follows the System.Text.Json semantics

Both the reflection path and the source generator now read the `Condition` property instead of treating any
`[JsonIgnore]` as an unconditional exclusion.

| Condition | 7.4.2 | 7.4.3 |
|---|---|---|
| `Always` (the default) | excluded | excluded (unchanged) |
| `Never` | excluded | **always emitted**, overriding the settings-level null/default discards |
| `WhenWritingNull` | excluded | omitted only when the value is null |
| `WhenWritingDefault` | excluded | omitted only when the value equals the member default |

Note the System.Text.Json naming trap: `JsonIgnoreCondition.Never` means "never ignore this member".

Two deliberate divergences from System.Text.Json: `WhenWritingDefault` compares against the member's *declared*
default (so `[JsonProperty(DefaultValue = ...)]` composes with it) rather than always `default(T)`, and
`WhenWritingNull` on a non-nullable value type is inert instead of throwing.

An attribute with no `Condition` property (for example the JSON.NET `[JsonIgnore]`) counts as unconditional, and
an unconditional ignore is checked **before** the `[DataContract]` opt-in gate, so it excludes the member even
next to a `[DataMember]` (see the breaking change above). What the `[DataMember]` gate does short-circuit are the
filters that run after it (`[IgnoreDataMember]`, the JSON.NET-style name matching). A **conditional**
`[JsonIgnore(Condition = ...)]` never changes membership: it records the per-member emission rule and falls
through to the `[DataMember]` gate, which is why
`[DataMember(EmitDefaultValue = false)]` + `[JsonIgnore(Condition = WhenWritingDefault)]` works on a
`[DataContract]` type.

### Non-public members: `[DataMember]` is enough on a `[DataContract]` type, `[JsonInclude]` everywhere else

**This is a wire change for `[DataContract]` types, stated loudly because members APPEAR in the output.** The
rule is hybrid, by ruling:

- **On a `[DataContract]` type, `[DataMember]` on a non-public member is honoured automatically** by the
  reflection path: private, internal, and protected fields and properties serialize and bind, and the
  non-public accessors of a public `[DataMember]` property (e.g. a private setter) are usable for
  deserialization. This is `DataContractJsonSerializer` fidelity: the DataContract model is
  accessibility-blind by definition, and the attribute pair is already the explicit declaration of intent.
  A DTO whose non-public `[DataMember]` members CrystalJson used to drop silently now produces the same
  membership DCJS did. If any consumer relied on those members being absent from CrystalJson's output, that
  wire changes with this release.
- **On a type without `[DataContract]`**, non-public members stay invisible unless annotated with
  `System.Text.Json`'s `[JsonInclude]`, unchanged (and deliberately a superset of System.Text.Json, whose
  reflection serializer rejects non-public members). A `[DataMember]` on a private member of a POCO does
  nothing, exactly as it did nothing under DCJS.
- `[JsonInclude]` alone still grants no membership on a `[DataContract]` type: `[DataMember]` is the opt-in
  there, as DCJS defined it. Where you added `[JsonInclude]` next to `[DataMember]` as the interim opt-in, it
  keeps working and is now simply redundant.

The source generator follows for `[JsonInclude]`: a non-public member (or the non-public accessor of a public
property) carrying the attribute is reached through **accessor thunks**: zero-cost `[UnsafeAccessor]` thunks
when the consuming target defines the attribute (net8+), reflection-based accessors otherwise (correct wire,
slower; a fallback, never a refusal). **`SYSLIB1038` is retired**: the generator no longer omits such members.
One deliberate residue: an `internal` member with NO include/exclude signal keeps its historical generated-only
inclusion (existing generated wires depend on it) and now gets the suppressible warning **`CJSON0012`**, which
nudges an explicit `[JsonInclude]` (included on both paths) or `[JsonIgnore]` (excluded on both); see
[Build and tooling](#build-and-tooling). `[DataMember]`-driven membership in generated containers ships in this
release too (see the breaking change above), and it takes precedence on a `[DataContract]` type: there,
`[DataMember]` is the only membership signal and accessibility does not filter, so this `internal`-member
residue does not apply.

### `[IgnoreDataMember]` now excludes the member

7.4.2 never read the attribute; the member serialized anyway. Both paths honor it now: on a type without
`[DataContract]`, a member carrying `[IgnoreDataMember]` disappears from the wire on write and is skipped on
read. **This is a wire change for any POCO that already carried the attribute.**

On a `[DataContract]` type the attribute stays inert, because the `[DataMember]` opt-in gate runs first. That
is `DataContractJsonSerializer` fidelity: DCJS ignores `[IgnoreDataMember]` on a `[DataContract]` type too.

### The foreign `[JsonConverter(typeof(...))]` spellings are honored

A member or type carrying System.Text.Json's or JSON.NET's `[JsonConverter(typeof(X))]` now serializes through
`X`, **when `X` implements the CrystalJson converter contract** (`IJsonPacker<T>` and/or `IJsonDeserializer<T>`
for the value's type). 7.4.2 ignored the attribute entirely, so this is a wire change for every DTO whose named
converter this library can run. A converter type it cannot run keeps being ignored, deliberately: a
half-migrated DTO whose converter only speaks System.Text.Json stays serializable with default handling.

A converter that exists only for CrystalJson belongs on the native attribute instead: see the
`[JsonConvertWith]` entry under [New APIs](#new-apis).

### Required members are enforced on read by the reflection path

Two related changes, both throwing `JsonBindingException` where a bind used to succeed silently:

- **C# `required` members** (non-nullable): a null-or-missing member now throws on the reflection path, the
  same contract the source-generated path always enforced ("Required JSON field ... was null or missing").
  Until now the reflection path recorded the flag and bound the member to its default without complaint, so the
  two paths disagreed on the same DTO.
- **`[DataMember(IsRequired = true)]` on a `[DataContract]` type**: a member ABSENT from the document now
  throws on read, DCJS-faithful; an **explicit `null` satisfies it**, deliberately distinct from C# `required`,
  where null also refuses. The write side is unchanged (`WithNullMembers()` remains the recipe for feeding a
  frozen legacy reader, which throws on the omitted null on ITS side).

If a stored document population legitimately misses such members, the fix is on the type (drop `required`, or
`IsRequired = false`), not on the reader: the flags now mean what they say.

### Dictionaries bind from the legacy DataContract array shape

`DataContractJsonSerializer` serializes `IDictionary<K, V>` as an array of `{"Key":..,"Value":..}` objects.
The dictionary binders now accept that shape on read, in the branch that previously always threw.

```json
[ { "Key": "a", "Value": 1 }, { "Key": "b", "Value": 2 } ]   // 7.4.2: JsonBindingException. 7.4.3: binds.
```

The object-map fast path is untouched and no previously-working input changes meaning. The reader is strict by
design: every element must be an object with exactly the two members `Key` and `Value` (exact casing), and one
non-conforming element fails the whole bind with a `JsonBindingException` naming its index. An empty array binds
to an empty dictionary. Generated converters inherit this for free, since their dictionary reads route through
the same runtime binders.

Dictionary types without a custom binder (for example `ImmutableDictionary`) still reject the legacy shape.

### The legacy/BCL collection types bind instead of throwing, or binding wrong

A systematic sweep of the collection categories that the DCJS-era corpus and the System.Text.Json support
matrix exercise, with one rule: every type either round-trips correctly or fails loudly with an actionable
message. What changed on read:

| Declared type | 7.4.2 | 7.4.3 |
|---|---|---|
| `Queue<T>`, `ConcurrentQueue<T>` | no binder, `JsonBindingException` | binds; wire order is dequeue order |
| `Stack<T>`, `ConcurrentStack<T>` | no binder | binds; the round-trip preserves the wire (the legacy serializers reversed a stack on every pass) |
| `ConcurrentBag<T>` | no binder | binds; content preserved, order unspecified |
| `ImmutableSortedSet<T>` | matched the `IImmutableSet<>` catch-all and received an `ImmutableHashSet<T>`, not assignable to the declared type: silent null | dedicated binder, correct type |
| `IReadOnlySet<T>` | received a `ReadOnlyCollection<T>` that does not implement the interface | binds to `HashSet<T>` |
| `IDictionary<K,V>`, `IReadOnlyDictionary<K,V>` as declared types | no binder | bind to `Dictionary<K,V>` |

Subclasses of `Collection<T>` (and user collection subclasses in general) also bind to the **declared** type
instead of a base shape, and the source generator no longer produces invalid converters for them.

Nothing that bound correctly in 7.4.2 changes meaning: the changes turn refusals and silent wrong shapes into
working binds.

### Enums serialize as strings by default, on every route

The default wire form for an enum flips from the numeric value to the string literal, on the text writer, the
DOM route and generated converters alike:

```csharp
enum Status { Active = 2 }
// 7.4.2: {"status":2}
// 7.4.3: {"status":"Active"}
```

This is a deliberate divergence from System.Text.Json: string enums keep payloads self-describing and read
naturally from JavaScript clients. **Reading is unchanged and tolerant in both directions**: names and custom
tokens bind case-insensitively, and numbers and numeric strings are still accepted. Pre-existing payloads
deserialize without any change, and a mixed fleet can roll forward incrementally.

To keep the numeric wire: `WithEnumAsNumbers()` on the settings, or
`[JsonProperty(EnumFormat = JsonEnumFormat.Number)]` per member, honored on both paths and on the DOM route.
`DataContractJsonSerializer` byte-parity requires the numeric form; the `DataContractCompat` preset
([New APIs](#new-apis)) already selects it. The old `OptionFlags.EnumsAsString` bit is retired, see
[Breaking changes](#breaking-changes).

### `[JsonBooleanLiterals]` takes one constructor, and a null false literal means "do not emit"

The two typed constructors (`string, string` and `int, int`) are replaced by a single
`JsonBooleanLiteralsAttribute(object? whenFalse, object whenTrue)`. **This is a binary break against 7.4.3-rc.1,
and it is source compatible**: `[JsonBooleanLiterals("0", "1")]` and `[JsonBooleanLiterals(0, 1)]` both still
compile unchanged against the new constructor, so consumers recompile and move on. Three constructors could not
coexist, because `[JsonBooleanLiterals(null, "1")]` binds to the typed `(string, string)` overload and fails there
before the `object` one is ever considered.

What the single constructor buys is a **null** first argument, meaning the member is not emitted at all when the
value is false:

```csharp
[JsonBooleanLiterals(null, "1")]    // true -> "1",  false -> member absent
[JsonBooleanLiterals(null, true)]   // true -> true, false -> member absent
```

The second is the idiom for "emit true, or emit nothing": the wire stays ordinary JSON booleans and the only
thing the attribute changes is the omission. It is exactly equivalent to `[JsonBooleanLiterals("0","1")]` plus
`[JsonIgnore(Condition = JsonIgnoreCondition.WhenWritingDefault)]`, and a test pins the two spellings
byte-identical. `[JsonIgnore(Condition = ...)]` remains the general mechanism for every other member type; this
is the boolean-specific spelling that states the intent.

Arguments accept a string, a bool, or a numeric value, and the two need not match. Because they are typed
`object`, the compiler no longer checks them, so both paths do: the reflection path throws at contract build and
the generator reports **`CJSON0017`**, with the same message.

One combination contradicts itself and warns. `StrictLiterals = true` rejects genuine JSON `true`/`false` in
favour of the configured literals, but when the false literal is null there is nothing on the false side to
enforce, because absence is what carries false. The generator reports **`CJSON0018`** at the member, as a
suppressible warning:

```csharp
[JsonBooleanLiterals(null, "1", StrictLiterals = true)]   // CJSON0018
```

Remove `StrictLiterals`, or give the member a real false literal. Both arguments are known at compile time, so
the contradiction is reported where it is written rather than discovered on a payload.

### Lifecycle callbacks now run, and the `StreamingContext` parameter is refused

The four `[OnSerializing]` / `[OnSerialized]` / `[OnDeserializing]` / `[OnDeserialized]` callbacks were never
invoked before this release. They are invoked now, on both write routes and on read, so a ported
`DataContractJsonSerializer` estate keeps the behaviour it had.

**Where they fire**, identically on the reflection path and in generated converters (pinned by a test that runs
the same type through both and compares): `[OnSerializing]` strictly before the first member is written and
`[OnSerialized]` strictly after the last, on both write routes; `[OnDeserializing]` on a constructed but
unpopulated instance, `[OnDeserialized]` on the fully populated one. Member converters run inside that bracket.

⚠️ **Proxies have no lifecycle.** A read-only or writable proxy is a lazy view over the JSON: nothing is
constructed and nothing is populated, so there is no interval for a pre/post pair to bracket. The callbacks run
when a value is **materialised** (`ToValue()`, `Deserialize`, `Unpack`). If your port has adopted "stay on the
proxy" as a principle, a callback will not run for you until something asks for the value. A type whose
invariants depend on a callback must be read as a value, not viewed through a proxy.

**Only the modern signatures are accepted.** `void M(StreamingContext)`, the signature DCJS requires, is refused:
the generator reports **`CJSON0015`** at the callsite, and the reflection path throws the same message when it
builds the type's contract. Both produce this text, which you can grep a build log for:

```
Remove the StreamingContext parameter from serialization callback '<name>', or replace it with JsonValue,
JsonObject or JsonArray. The legacy DataContractJsonSerializer callback signature is not supported.
```

This is a deliberate, limited breaking change: source compatibility is kept wherever possible, and breaks are
accepted where the fix is trivial. This one is a search and replace over the callsites.

#### The sweep recipe

**Precondition, check this before you change anything.** DCJS *requires* the `StreamingContext` parameter and
refuses `void M()` just as hard as we refuse the parameter. So converting a callback **costs that type its DCJS
compatibility**. A type must therefore be converted together with every service that serializes it. If a DTO is
shared between a converted service and one still running on DCJS, they move together or not at all. Establish
which types are still reachable from a DCJS endpoint first; do not begin the sweep until that list is empty for
the types you intend to convert.

Then, per type:

1. Find the callbacks: search for `[OnSerializing]`, `[OnSerialized]`, `[OnDeserializing]`, `[OnDeserialized]`,
   then take the method each one sits on.
2. Every such method has exactly two legal outcomes:
   - **Remove the parameter**, giving `void M()`. This is the default; take it whenever the body does not use
     `context`.
   - **Replace the parameter** with `JsonValue`, `JsonObject` or `JsonArray`, giving for example
     `void M(JsonObject document)`. Take this only on `[OnDeserializing]` / `[OnDeserialized]`, and only when the
     callback needs to inspect the incoming payload. The parameter then receives the document being bound, which
     is a capability DCJS never had. Pick `JsonObject` unless the type binds from an array.
3. Delete any remaining use of the `context` value inside the body. It carried no information this serializer
   provides.
4. Rebuild. Any callsite you missed is a build error carrying the text above.

Do not pass `null` for the parameter to keep the old signature compiling: the callback may dereference it, and a
`NullReferenceException` is a bad way to discover that.

#### `[OnDeserializing]` and `required` / `init`-only members cannot share a type

This is the second error the sweep runs into, and unlike the first one the fix is a design choice rather than a
mechanical edit, so it is worth knowing about before you start.

A pre-populate callback must observe a **constructed but unpopulated** instance. Generated code therefore
constructs first and assigns the members afterwards, as statements. A `required` member can only be set in an
object initializer, and an `init`-only member likewise, so neither can be assigned that way. The generator
reports **`CJSON0016`** on the type, naming the offending member, with the remedy that fits the modifier:

```
Remove the 'required' modifier from member 'Total' of type 'Order', or remove [OnDeserializing] from that
type. A pre-populate callback must observe an unpopulated instance, so members are assigned after
construction, and a 'required' member can only be set in an object initializer.
```

```
Change the 'init' accessor of member 'Total' of type 'Order' to 'set', or remove [OnDeserializing] from that
type. A pre-populate callback must observe an unpopulated instance, so members are assigned after
construction, which an init-only member does not allow.
```

Neither construct is a problem on its own: this fires only when both are present on the same type. Without the
diagnostic the consumer would instead get a compiler error inside generated source they never wrote.

**This is a generated-path constraint only.** The reflection path assigns members reflectively, where neither
modifier applies, so the same type round-trips there without complaint. A type can therefore serialize happily
today and stop the build the moment it is enrolled in a generated container.

Of the three ways out, dropping `[OnDeserializing]` is usually the right one: it is the only callback of the
four with this constraint, and `[OnDeserialized]` runs on the fully populated instance with no restriction at
all. Reach for it unless the callback genuinely has to seed state that the incoming document then overwrites.

### Two IL-level shape changes behind the new attribute hierarchy

`CrystalJsonConverterAttribute` and `CrystalJsonSerializableAttribute` (formerly `CrystalJsonSerializable`) now
sit under the new format-neutral base classes:

- `CrystalJsonConverterAttribute` derived directly from `System.Attribute`; it now derives from
  `CrystalConverterAttribute`.
- `CrystalJsonSerializableAttribute` declared its own `Type[] Types { get; set; }` property; that property is
  now inherited from `CrystalSerializableAttribute`, and the attribute's own declaring type carries no `Types`
  member of its own.

**Both changes are source-compatible**: existing code that references either attribute, or reads `.Types`,
recompiles unchanged against the new version, and nothing in ordinary usage (attribute construction, property
access, the source generator's own `ForAttributeWithMetadataName` lookup, which matches by exact metadata name
regardless of the base type) is affected. The only population that can observe a difference is code doing its
own reflection over a **precompiled** assembly built against the old shape - for example, code that walks
`GetType().BaseType` expecting `System.Attribute` directly, or that looks up `Types` with
`BindingFlags.DeclaredOnly` expecting it on the attribute's own type rather than inherited. If you have such
code (most applications do not), recompile it against the new package rather than mixing binaries.

### One nesting-depth cap for every serialization format: `CrystalJsonWriter.MaxDepth = 64`

The two JSON writers each carried their own private depth cap of 16 levels, the generated paths had none, and
the JSON parser refused past 64. All formats and the parser now share a single named constant,
`SnowBank.Data.Json.CrystalJsonWriter.MaxDepth = 64` (`CrystalXml.MaxDepth` is kept as an alias pointing at the
same constant). The value is the default maximum depth of both System.Text.Json and Newtonsoft.Json, so a
document this library writes stays readable by the mainstream .NET stacks at their defaults, and anything this
library writes it can read back. For the JSON writers this is **strictly a loosening** (64 up from 16): no
object graph that serialized successfully before can start failing. The generated paths, which previously had
no cap at all, now refuse past 64 with a typed exception instead of overflowing the stack.

### `[CollectionDataContract]` naming has no JSON existence, on either serializer

`Name`, `ItemName`, `KeyName` and `ValueName` shape the XML wire only. `DataContractJsonSerializer` ignores all
four when it writes JSON, so there is nothing for a migration to reproduce:

```csharp
[CollectionDataContract(Name = "ItemBag",  ItemName = "entry")]                       public class ItemBag  : List<string> { }
[CollectionDataContract(Name = "LabelMap", KeyName  = "code", ValueName = "label")]   public class LabelMap : Dictionary<string, string> { }
```

```json
{ "bag": ["x","y"], "labels": [ { "Key": "c1", "Value": "Label one" } ] }
```

That is the legacy serializer's own output: plain array elements, and the literal `Key`/`Value` rather than
`code`/`label`. The attribute's only JSON-visible meaning is "this type is a collection", which the collection
binders already provide for subclasses of `List<T>`, `Collection<T>` and `Dictionary<K,V>`: such a type is
constructed and filled as itself, so `Bag` comes back an `ItemBag` and `Labels` a `LabelMap`. Under
`CrystalJsonSettings.DataContractCompat` the dictionary takes the pair-array form above and binds back from it.

Migration action: none. If a port has scheduled work to carry these names across, delete that work item.

### Microsoft-format dates with an offset suffix preserve the instant

In `"/Date(ms+HHMM)/"` the milliseconds are always the UTC epoch offset; the suffix only carries the producer's
local offset (`DataContractJsonSerializer` emits it for `DateTimeKind.Local` values). The reader used to shift
the value by (reader-local offset minus suffix offset), which produced a different instant on any machine whose
offset differed from the suffix, and could not round-trip CrystalJson's own `WithMicrosoftDates()` output.

`JsonString.ToDateTime` now surfaces the instant in the reader's local time (same as DCJS) and
`ToDateTimeOffset` keeps both the instant and the producer's offset. `TryConvertToDateTimeOffset` used to throw
`ArgumentException` on such a value instead of converting; it now converts.

If you have test expectations pinned to the old shifted results, they will need updating. They were also
machine-offset dependent, so they only ever held on one time zone.

### Three more date and number read fixes

- **A localized long date parses on every platform.** A letter-starting date string only tried the strict
  `ParseExact` forms and failed without reaching the lenient `DateTime.Parse` fallback. macOS and Linux CLDR
  data puts a narrow no-break space (U+202F) before AM/PM where Windows uses a regular space, so a date
  formatted on one platform refused to parse on the other. It now falls through and parses.
- **`JsonDateTime` extremes convert without offset arithmetic.** Converting a DOM-packed `DateTime.MinValue`
  to `DateTimeOffset` threw `ArgumentOutOfRangeException` east of Greenwich (and `MaxValue` west of it). The
  extremes are sentinels ("no value", "the end of time") and now map to the canonical
  `DateTimeOffset.MinValue` / `MaxValue` regardless of the machine's offset, so the DOM route round-trips a
  DTO with an unset date the same way the text route always did.
- **Decimal scale survives the DOM.** `JsonNumber.ToDecimal` converted through the `double` value, so binding
  the literal `1.100` yielded `1.1m` (scale 1) instead of `1.100m` (scale 3): money-display digits changed
  after a round-trip through the DOM. The conversion now recovers the value from the original literal.

### `ColaRangeSet.Mark` accepts a degenerate range instead of throwing

`ColaRangeSet<TKey>.Mark(begin, end)` threw `InvalidOperationException` when `begin == end`. An empty
range contains nothing, so it is now a no-op: the set, its `Count` and its `Bounds` are unchanged.
A **backwards** range (`begin > end`) still throws, since that is a genuine caller error.

This matches how a real cluster treats an empty conflict range, which is where it surfaced: a range
read whose conflict range resolves as empty (for example a reversed limited read whose end selector
lands exactly on the last returned key) crashed against the emulator while the real cluster accepted
it.

If you guarded a `Mark` call against the degenerate case, or caught `InvalidOperationException`
around one, that code is now dead.

The exception message for the backwards case was also printing the begin key under the *End key*
label and the end key under *Begin key*. If you have a log parser or a test keyed to that text, it
changed.

### `ColaOrderedDictionary` range removal no longer crashes when the search exhausts

`ColaOrderedDictionary.RemoveRange` and `IterateAndRemoveRange` threw `IndexOutOfRangeException`
when the range search ran out of entries: on an empty dictionary, on a range above every key, or
when the removals consumed every key at or after the start of the range.

An operator-precedence slip guarded the exhausted-search case, and for every non-exhausted iteration
the wrong parse happened to compute the intended predicate, which is why it stayed latent since the
type was written. Only code that actually hit the crash sees a difference. If you are catching
`IndexOutOfRangeException` around a range removal as a workaround, that catch is now dead and should
go.

### `Slice` fixed-width encoders: two wire-level fixes

Two members of the fixed-width family produced wrong bytes: `Slice.FromFixedU16BE` returned a slice larger
than the two bytes it had written, and the `FromFixed128BE(upper, lower)` split overloads emitted
little-endian bytes. Both now produce what their names promise, pinned by tests over the whole split family.
Keys stored through the broken overloads do not match the corrected output.

### The transaction dump printed read conflicts under the write-conflict label

The second dump site of the transaction debugger read the read-conflict set under its "Write Conflicts"
heading, so a dump printed the same set twice and reported zero write conflicts while the transaction held
them. If a log parser or a test keyed on that text, it changed. The conflict-marking logic itself was always
correct; only the dump lied.

### Native future callbacks are reworked, and shutdown drains deterministically

The completion path from the native client into managed code moved to a single `UnmanagedCallersOnly`
callback with pooled value-task sources. Two effects you can observe: less allocation per operation, and a
deterministic drain of pending futures on `Fdb.Stop()` and database dispose, which closes the long-standing
shutdown races (issue #48). The netstandard2.0 build keeps the marshaled-delegate path.

`FdbAspireHostingExtensions` carries the last-known docker image tag per major, used when you do not pin one.

## New APIs

### CrystalJson/CrystalXml: format-neutral container attributes and the output truth table

Declaring a source-generated container is now split into three independent concerns: which class hosts the
generated code (`[CrystalConverter]`), which format(s) it produces (`[CrystalJsonOutput]` and/or
`[CrystalXmlOutput]`), and which types it enrolls (`[CrystalSerializable(typeof(...))]`, format-neutral - the
enrolled type gets a generated serializer for every format the container requests).

```csharp
[CrystalConverter]
[CrystalJsonOutput(CrystalJsonSerializerDefaults.Web)]
[CrystalXmlOutput]
[CrystalSerializable(typeof(User))]
[CrystalSerializable(typeof(Product))]
public static partial class ApplicationSerializers
{
    // generated code will be inserted here
}
```

`[CrystalJsonConverter]` and `[CrystalXmlConverter]` remain as mono-format aliases (marker + a single output
format bundled together) for the common case of a container that only ever produces one format. A container
combining an alias with an explicit output attribute, one that names no output format at all, or one carrying
several container markers, is refused at build time - see [Diagnostics](#diagnostics-reference) below.

`CrystalOutputAttribute` is the (non-generated-code-visible) common base of `[CrystalJsonOutput]` and
`[CrystalXmlOutput]`, kept purely for documentation and discoverability: the source generator matches each
output attribute by its exact metadata name, not by walking this hierarchy, so a type derived from
`CrystalConverterAttribute`, `CrystalOutputAttribute`, or `CrystalSerializableAttribute` is invisible to it and
does not enroll as a recognized format or container marker. Do not subclass any of the three.

The full truth table, the execution pipeline, the compat (`DataContract`) and modern XML profiles, and every
diagnostic in detail are documented in [`Documentation/CrystalXml.md`](../CrystalXml.md); this entry only
summarizes what changed relative to 7.4.2.

#### Diagnostics reference

One line each, for the diagnostics introduced or reshaped by this release:

| Diagnostic | Severity | Meaning |
|---|---|---|
| `CRYS0001` | Error | `[CrystalConverter]` names no output format; the container would generate nothing |
| `CRYS0002` | Error | A mono-format alias (`[CrystalJsonConverter]`/`[CrystalXmlConverter]`) is combined with an output attribute, which the alias cannot express |
| `CRYS0003` | Error | A container carries several container markers, which is two answers to "what does this container produce" |
| `CJSON0010` | Error | `[JsonConvertWith]` names a type that implements neither `IJsonPacker<T>` nor `IJsonDeserializer<T>` for the member's type |
| `CJSON0011` | Error | A member declares two different wire names for two serializers (`[DataMember(Name = ...)]` next to a disagreeing foreign rename) |
| `CJSON0019` | Warning | A `[CrystalSerializable]` enrollment names a type CrystalJson already serializes natively; no converter is generated for it |
| `CJSON0020` | Info | The generated JSON proxy surface (`ToReadOnly`/`ToMutable`, the proxy types) is skipped because the compilation is below .NET 7+/C# 11; the converter, `TypeMapper`, and any requested XML output are unaffected |
| `CJSON0021` | Error | A `[CrystalSerializable]` enrolls a type the compiler cannot resolve; fix the compile error on the enrolled type |
| `CXML0001` – `CXML0013` | mostly Error, `CXML0012` Info | The XML-specific rules (DataContract format vs naming policy, missing serializer container, invalid attribute projections, name collisions, missing inner-item names, invalid XML names, converters without an XML facet, `[CollectionDataContract]` not honored on the DataContract format, dictionary shapes with no lexical form, inert settings, and the get-only `[DataMember]` property that the compat format refuses) - see `Documentation/CrystalXml.md` for the full table |

### CrystalJson: the `DataContractCompat` preset, and legacy duration emission

`CrystalJsonSettings.DataContractCompat` is a named, cached preset that reproduces the **complete**
`DataContractJsonSerializer` wire: numeric enums, `\/Date(ms)\/` dates, ISO 8601 duration strings for
`TimeSpan`, `[{"Key":..,"Value":..}]` dictionaries, and explicit `null` members. An endpoint that must feed an
unchanged legacy reader becomes one settings reference instead of a five-call composition (which stays
byte-equivalent: the preset and the fluent chain are the same cached instance). Scope it per endpoint: the
explicit-null emission in particular is pure verbosity for any consumer that is not a frozen legacy reader.

The duration half is new as well: `WithIso8601Durations()` serializes `TimeSpan` as the legacy
`"P1DT2H3M4.005S"` form instead of the default number of seconds (`WithNumericDurations()` restores the
default), on both the text and DOM routes. Reading accepts both forms regardless of settings.

A source-generated container can bake the preset as its default wire:
`[CrystalJsonConverter(CrystalJsonSerializerDefaults.DataContractCompat)]` makes the container's generated
entry points emit the legacy wire when the caller passes no settings, while explicitly passed settings always
replace the profile entirely. The profile governs value formats only and is independent of membership: it
serves plain DTOs under the DCJS POCO opt-out rules, and `[DataContract]` types under the DataContract model
(see the breaking change above), the same way an unprofiled container does. For the types it serves, such a
container produces what DCJS would have produced, with the documented differences (member order, no `\/`
escaping outside date literals, `-0.0` as `0`, and loud refusals where DCJS resolved
two-serializer conflicts silently). Combining the profile with a naming policy (camelCase and friends) is
refused at build time (**`CJSON0013`**); `PropertyNameCaseInsensitive` is not refused, since it only governs
how an incoming member name is matched on read and changes nothing the profile writes. The intended shape for
a progressive portage is the dual container: legacy services on the
compat container, modernized ones on a default or `Web` container over the same types; delete the legacy
container when the portage completes.

### CrystalJson: legacy dictionary emission

`CrystalJsonSettings.WithDictionariesAsPairArrays()` serializes every dictionary as
`[ {"Key":..,"Value":..}, ... ]` instead of a JSON object map, for legacy clients that cannot read maps. It is
off by default, and the shape is always accepted on read regardless.
`WithDictionariesAsMaps()` restores the default.

Keys are emitted with their natural JSON type (string keys as strings, numeric keys as numbers), matching DCJS.
The switch is honored by both the reflection path and generated converters, since both go through the text
writer. The DOM route keeps the object-map model, because a `JsonObject` *is* a map: serialize through the text
writer to produce the legacy shape.

### CrystalJson: `[JsonConvertWith]`, the native converter attribute

`[JsonConvertWith(typeof(X))]` attaches a CrystalJson converter to a member or a type, where `X` implements
the `IJsonPacker<T>` / `IJsonDeserializer<T>` pair. Both paths recognize it, feeding the same slot as the
foreign spellings. Recognition is **per facet**: a type that implements only one half serves that direction,
and default handling covers the other, which is the recipe for asymmetric serialization.

The doctrine: keep System.Text.Json's `[JsonConverter(typeof(...))]` only when the named converter is valid
for System.Text.Json as well, so both serializers do the same thing. A CrystalJson-only converter behind the
STJ attribute poisons the type for STJ (a runtime `InvalidOperationException`, or an STJ source-gen build
error); such a converter carries the native attribute, which STJ never inspects.

Precedence when several apply: the native attribute wins over `[JsonBooleanLiterals]` and over both foreign
`[JsonConverter]` spellings. And unlike the foreign spellings, a `[JsonConvertWith]` naming a type without
the Pack/Unpack pair fails loudly: a metadata-construction exception on the reflection path, build error
**`CJSON0010`** through the generator. It is our own attribute; silence would only hide a typo.

### CrystalJson: member converters for the nullable form

A member converter can now be declared for the nullable form itself: `IJsonMemberConverter<DateTime?>` (or a
single facet of it) on a `DateTime?` member. The bridge probes the member's **exact** type first, then falls
back to the existing lift, on both the reflection path and the generator, so every `T` converter keeps working
unchanged - and nothing could depend on the `T?` form before, since it was refused on the native path and
ignored on the foreign one.

The point of the `T?` form is the **present-but-unreadable** input: legacy converters (DCJS-era protocols in
particular) often treat an empty or unparseable string as "no value", and a converter declared for `T` can
never answer that, because it must return a `T`. Declared for `T?`, the converter owns every *present* value
and can answer `null` - distinctly from `default(T)`, which remains a legitimate domain value (`0` for an
`int?`, year 1 for a `DateTime?`), and from JSON null or a missing member, which the pipeline still handles
before the converter on **both** sides. That last part means the `T?` declaration transfers the read side
only: `Pack` never sees null, and the null-member wire keeps following the settings (`WithNullMembers()`
etc.), so a legacy converter whose null-member *write* form is not JSON null (e.g. an empty string) remains
non-portable on the write side by design. A `T?` converter named on a NON-nullable member stays a loud
refusal on both paths.

### CrystalJson: self-serializable types

`[CrystalJsonSelfSerializable]` is a **meta-attribute**: you apply it to one of *your own* attribute classes, and
every type decorated with that attribute is opted into JSON source generation. A layer can opt its own types in
without coupling the consuming application to the generator.

```csharp
// the layer declares its marker attribute once
[CrystalJsonSelfSerializable]
public sealed class MyEntityAttribute : Attribute { }

// the application just declares an entity
[MyEntity]
public sealed partial record Widget { public required string Name { get; init; } }
```

A marked type acts as its own container. Everything generated lands inside **one** nested static class named
`Json`, so the entity reserves exactly one member name:

```csharp
Widget.Json.Default          // the converter
Widget.Json.ReadOnly         // read-only proxy
Widget.Json.Writable         // writable proxy
Widget.Json.PropertyNames    // property-name constants
Widget.Json.GetResolver()    // the per-container resolver
```

Types referenced by the entity are still crawled and nest inside that same scope under their plain names, where
they cannot shadow the referenced type in the entity's own source. The single reserved name is deliberate: a
future generator for another format claims a sibling scope (`Widget.Cbor`) without renegotiating anything. It
also means the whole `Json` scope is generated code, so it carries the generated-code attributes that could not
be placed on the entity partial, which is your source. Self-mode hint names are namespace-qualified, since
entity names collide far more often than container names do.

Constraints and their diagnostics:

| Diagnostic | Severity | Cause |
|---|---|---|
| `CJSON0004` / `CJSON0005` | error | the entity is not `partial`, or is generic, or is nested |
| `CJSON0006` | error | the entity already declares a member named `Json`. Rename it and keep the wire name with `[JsonProperty("json")]`, or use a `[CrystalJsonConverter]` container instead |
| `CJSON0007` | warning | a referenced type is named like a scope member; it is excluded from generation and falls back to runtime serialization |

The existing `[CrystalJsonConverter]` container path is untouched.

### Testing.Framework.Playwright: builder hooks

`SnowBank.Testing.Framework.Playwright` gained five extension points on the component builder:

| Hook | What it does |
|---|---|
| `WithBrowserOptions(o => ...)` / `WithContextOptions(o => ...)` | tweak the Chromium launch and browser-context options (viewport, UserAgent, ...) on top of the component defaults, without replacing the whole options object |
| `WithInitScript(js)` | inject a context-level init script, evaluated before the first page, after the package's own scripts |

### Experimental: `FdbTextIndex`

`FoundationDB.Layers.Experimental` gained a full-text search layer with term, phrase and proximity queries and a
weighted-sum (BM25-style) scorer.

**This layer is experimental**: it lives under `Layers.Experimental` precisely because its keyspace layout and
its API are still free to move between minor versions. Do not put a production index on it yet.

### `FdbErrorDebugger`: the client's error translation, exposed for test oracles

`FoundationDB.Client` gained a small static proxy over the native client's error-translation
internals, so test code can observe them without an `InternalsVisibleTo` grant. It is the error-side
companion of the existing `FdbTransactionDebugger`.

```csharp
FdbErrorDebugger.GetErrorMessage(code);                                  // fdb_get_error
FdbErrorDebugger.MapToException(code);                                   // the exception the client would throw
FdbErrorDebugger.TestErrorPredicate(FdbErrorPredicate.Retryable, code);  // fdb_error_predicate
```

Its intended use is as an **oracle**: conformance suites pin the native client's answers and hold
emulator behavior against them.

⚠️ **This does not change how you handle errors, and you should not use it to.** Error handling
belongs to the retry loop (`db.ReadAsync` / `WriteAsync` / `ReadWriteAsync`), which already applies
these predicates for you. Reading `TestErrorPredicate(Retryable, ...)` in application code to decide
whether to retry re-implements the loop by hand, badly, and is the exact mistake the retry loop
exists to prevent. Nothing in your existing error handling needs to change because this type now
exists.

Every member calls into `fdb_c`, so no cluster connection is needed, but the native library must be
deployed or the call throws `DllNotFoundException`.

### CrystalJson: `[JsonProperty(NumberFormat = String)]`, numbers as strings

A numeric member can opt into the string form, the same per-member knob as `EnumFormat`:

```csharp
[JsonProperty(NumberFormat = JsonNumberFormat.String)]
public long AccountId { get; init; }
// => {"AccountId": "12345678901234567"} instead of {"AccountId": 12345678901234567}
```

The string is exactly the literal that the numeric form would have produced (decimal scale
included), which protects 64-bit values from the precision loss of JavaScript consumers.
Reading always accepts both forms, with or without the attribute, so producers and consumers
move independently. Honored by the reflection path, generated converters, the DOM route, and
the writable-proxy setters, with a byte-parity test across the paths. No default changes:
members without the attribute keep the numeric form.

### `FdbException` messages come from a managed table

`FdbErrorMessages.TryGetMessage(FdbError)` is a 337-entry table generated from the deployed client's own
`fdb_get_error` answers, pinned byte-equal by a test. `FdbException(FdbError)` resolves through it, so the
code-only constructor works on a process without `fdb_c` (FakeDb and other managed backends), and a known
code costs no interop call. `fdb_get_error` remains the fallback for a code newer than this build.

### FakeDb: a pluggable committed store, and closer conformance

The in-memory emulator's committed data moved behind a public extension point in the new
`FoundationDB.Storage` namespace: `IFdbCommittedStore` and `IFdbCommittedCursor`, with `ColaCommittedStore`
as the built-in backend. An out-of-assembly backend can now plug in its own storage.

The release also carries a conformance campaign that holds the emulator against a real cluster: selector
resolution around pending atomic operations, `CompareAndClear` read-conflict retention, and boundary-key
anchoring for `GetKey` and `GetRange` now match the real client where they diverged. A test pinned to the
emulator's old, wrong answer sees the corrected one.

### FdbTop and FdbShell

`FdbTop` now parses command-line arguments instead of only reading defaults. Both tools gained a `README.md`,
and `FdbShell` no longer produces an empty command token when ENTER completes a command that takes no
arguments.

### Smaller additions

- `BitMap64.FindSpan(span, start)`: the index of the first run of N contiguous set bits.
- `SimpleTest.ShouldNotHappenWithin(condition, duration, message)`: asserts that a condition stays false for
  the whole duration, in sync and async forms; the negative counterpart of the existing settle helpers.
- The packet-capture decoder (`SnowBank.Networking.PacketCapture`) decodes leniently and no longer throws on

## Build and tooling

Only relevant if you build the SDK from source, consume it as a submodule, or run its test suites.

- **.NET 11 preview 6.** The SDK pin in `global.json` is `11.0.100-preview.6.26359.118`, and the Microsoft
  package wave moved to `11.0.0-preview.6.26359.118` (net11 leg) and `10.0.10` (net10 and net8 legs).
  The libraries still multi-target `net8.0`, `net10.0` and `net11.0`: **the .NET 8 floor did not move.**
- **`dotnet test` now needs an opt-in in `global.json`.** Every test project uses the NUnit
  Microsoft.Testing.Platform (MTP) runner, and VSTest is gone from the workflow. On the .NET 10+ SDK,
  MTP v2 refuses to run under the old VSTest bridge and fails with *"Testing with VSTest target is no
  longer supported by Microsoft.Testing.Platform"*. If you build this repository from source, or you run
  MTP suites of your own, add the test runner to your `global.json`:
  ```json
  {
    "test": { "runner": "Microsoft.Testing.Platform" }
  }
  ```
  The `TestingPlatformDotnetTestSupport` MSBuild property was the bridge for the old path and no longer
  has any effect on .NET 10+. **Scope the run to a modern target** (`-f net10.0`): MTP mode requires every
  project in the run to use the MTP runner, so a solution that still has `net472` legs (this repository
  has four) is rejected with *"All projects must use that test runner"* unless the TFM is scoped. The
  net472 legs keep the NUnit console runner, unchanged. Running the test assembly directly works either
  way, and skips the build:
  ```bash
  dotnet artifacts/bin/<Project>/debug_net11.0/<Project>.dll --filter "FullyQualifiedName~<NamePart>"
  ```
- **The JSON source generator's language floor is C# 9, checked explicitly.** The generator's first act is a
  language-version gate that reports **`SYSLIB1221`** ("language version not supported by the source generator")
  and stops when the compilation is below C# 9. `<LangVersion>latest</LangVersion>` clears it with margin, but
  the actual requirement is only `>= 9`; the classic trigger is a ported project still pinning a
  netfx-era `<LangVersion>7.3</LangVersion>`.
- **Generated JSON code no longer relies on the project's global usings.** The generated files emit no `using`
  directive and now fully qualify every BCL name, and they are warning-free under their own `#nullable enable`
  even for members declared in a nullable-oblivious project. Projects that enabled `ImplicitUsings` (or added
  manual global usings) only to stop `CS0246` walls inside generated files can drop that workaround, and
  warnings-as-errors builds no longer trip on `CS8600`/`CS8603`/`CS8625` in generated code.
- **CS1591 (missing XML doc comment) is muted on Release builds.** Debug builds are unaffected, so the
  warnings are still there while you work.
- **New diagnostic `CJSON0012`** (warning, suppressible): an `internal` member with no include/exclude signal
  is serialized by generated converters but invisible to the reflection path. The inclusion is kept for wire
  compatibility; the warning makes the divergence observable so the intent gets pinned with `[JsonInclude]` or
  `[JsonIgnore]`. (`SYSLIB1038` no longer fires: non-public `[JsonInclude]` members are now generated through
  accessor thunks instead of being omitted.)
- **New diagnostics `CJSON0004` / `CJSON0005`**, reported on a self-serializable type that is not `partial`, is
  generic, or is nested.
- **New scripts**: `scripts/build.ps1` / `scripts/pack.ps1` (and `.sh` twins) for standalone builds, and
  `scripts/check-fdb-image-tags.ps1` / `.sh` to refresh the Aspire docker tag constants from Docker Hub.
- **`DownloadBinaries.sh`** joins `DownloadBinaries.ps1` in `FoundationDB.Client.Native/` to fetch the native
  `fdb_c` binaries on macOS and Linux (needs `curl` and `python3`).
- **`SliceReader` reads are GC-safe on the netstandard2.0 build.** The lite span shim handed out pointers the
  GC does not track, so a compaction between capture and read could decode stale bytes; observed as
  nondeterministic net472 failures under memory pressure. The lite path now goes through tracked references.
- **Generated code no longer breaks on a value-type `T?` or a read-only member.** A `GenericBox<int>`-style
  substitution emitted `Nullable<int>` where `int` was declared, and a get-only member received an
  object-initializer assignment (`CS0200`). A read-only member is now serialization-only: written to the
  wire, skipped on read.
- **`CORESDK_STANDALONE_BUILD`** is set when the repository is built standalone rather than as a submodule.
- **net472 legs** now force `PlatformTarget=x64` and suppress the TFM-support build warnings.
- `SnowBank.SourceAnalysis` was extracted as a shared Roslyn helper library, consumed **by source**, not as a
  package: it changes nothing for consumers.
- **The XML certification suite now runs on the net472 validation target as well**, alongside the existing
  netstandard2.0 build check: the lite path is exercised on the real .NET Framework CLR for XML output exactly
  as it already was for JSON.
- **Generated code for an XML-only container compiles on the lite (netstandard2.0/net472) consumer.** No
  language or runtime feature specific to XML emission requires more than the generator's existing floor.

- `CrystalJsonSettings.AllowTrailingData()` and `WithoutComments()` are sometimes assumed to be new here.
